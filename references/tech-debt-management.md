# 技术债管理指南

> 基于技能实战多轮开发实战总结。技术债是技能多轮迭代后必然积累的问题，不管理会导致技能越来越难维护、bug越来越多。
> 核心结论：**技术债不是"以后再修"，而是必须有定期审计+分类管理+偿还计划的持续过程。实战中，rules.py有17个无用函数、scripts目录有16个脚本职责不清、多个信号孤岛，这些都是技术债。**

---

## 一、什么是技能的技术债

### 1.1 定义

技能技术债是指在技能开发过程中，为了快速交付或临时修复而采取的不完美方案，导致后续维护成本增加、质量下降的问题。

### 1.2 技能技术债的7种类型

| 类型 | 说明 | 实战案例 |
|------|------|---------------|
| **死代码** | 不再使用的函数/类/脚本/文档 | rules.py有17个无用函数 |
| **重复代码** | 多个脚本里有相同的逻辑 | stats.py和upload_history.py都有resolve_base_token |
| **职责不清** | 一个脚本做太多事，或多个脚本做同一件事 | 16个脚本，notify.py合并到cloud_write.py但文件还在 |
| **信号孤岛** | 指标计算了但没有被决策树/分析使用 | 多项指标中10项从未被引用 |
| **文档过时** | 文档描述与实际代码不一致 | script-reference.md列出的脚本与实际scripts目录不符 |
| **配置混乱** | 凭据硬编码、配置分散在多个文件 | 早期config.py不存在，每个脚本自己写token |
| **测试缺失** | 没有端到端测试，改了不知道会不会坏 | 多轮修改后从未完整跑通start→continue→settle |

### 1.3 技术债的危害

```
短期危害：
  - 修改一个地方，意外破坏另一个地方（蝴蝶效应）
  - LLM不知道该用哪个脚本/函数，导致能力闲置
  - bug定位困难，因为代码路径不清晰

中期危害：
  - 新功能开发速度越来越慢
  - 修复一个bug引入两个新bug
  - 技能评分停滞不前甚至下降

长期危害：
  - 技能无法维护，只能重写
  - 用户失去信心
  - 之前的开发投入全部浪费
```

## 二、技术债审计方法

### 2.1 定期审计（每10期或每月一次）

**审计清单**：

```
【死代码审计】
  - 每个函数：被调用了吗？调用方是谁？
  - 每个脚本：被SKILL.md或orchestrator引用了吗？
  - 每个文档：被SKILL.md引用了吗？内容与实际一致吗？
  - 每个指标：被决策树或分析使用了吗？

【重复代码审计】
  - 搜索相同的函数名/变量名/逻辑片段
  - 检查是否有多个脚本做同一件事
  - 检查配置是否分散在多个文件

【职责不清审计】
  - 每个脚本的职责是否单一？
  - 脚本之间的依赖关系是否清晰？
  - 是否有循环依赖？

【信号孤岛审计】
  - 每个指标：被决策树引用了吗？被分析引用了吗？
  - 每个方案类型：被决策树评分了吗？被推荐过吗？
  - 每个方法论：被引用过吗？

【文档一致性审计】
  - SKILL.md描述的脚本与实际scripts目录一致吗？
  - references文档的内容与实际代码一致吗？
  - 版本号与实际更新日期一致吗？

【配置审计】
  - 凭据是否外置到config.py？
  - 是否有硬编码的token/key？
  - 环境变量覆盖是否正常工作？

【测试覆盖审计】
  - 是否有端到端测试？
  - 每个脚本是否单独测试过？
  - 修改后是否回归测试？
```

### 2.2 技术债分级

| 级别 | 定义 | 处理时限 | 技能案例 |
|------|------|---------|-----------|
| **P0 阻塞** | 导致技能无法运行或核心功能失效 | 立即修复 | 非UTF-8编码导致脚本崩溃 |
| **P1 严重** | 导致功能异常或数据错误 | 24小时内修复 | continue缺路由模式字段报错 |
| **P2 中等** | 影响可维护性或用户体验 | 本周内修复 | rules.py 17个无用函数 |
| **P3 低** | 代码质量问题，不影响功能 | 下次迭代修复 | 变量命名不规范 |

### 2.3 技术债登记

**技术债登记表**（写入云端数据库或本地JSON）：
```
- ID（唯一标识）
- 类型（死代码/重复代码/职责不清/信号孤岛/文档过时/配置混乱/测试缺失）
- 级别（P0/P1/P2/P3）
- 位置（文件/函数/行号）
- 描述（具体是什么问题）
- 影响（不修复会怎样）
- 修复方案（怎么修）
- 修复成本（预估工作量）
- 状态（待修复/修复中/已修复/已验证）
- 创建日期
- 修复日期
```

## 三、技术债偿还策略

### 3.1 偿还优先级排序

```
排序公式：优先级 = 级别权重 × 影响范围 × 修复紧迫性

级别权重：P0=100, P1=50, P2=20, P3=5
影响范围：影响1个脚本=1, 影响3个脚本=3, 影响全流程=10
修复紧迫性：用户已反馈=3, 影响新功能开发=2, 不影响=1
```

### 3.2 偿还方式

| 方式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **直接删除** | 确认无用的死代码 | 最简单，立即见效 | 可能误删仍在使用的代码 |
| **合并重构** | 重复代码/职责不清 | 提升可维护性 | 风险较高，需要充分测试 |
| **迁移整合** | 配置混乱/信号孤岛 | 统一管理 | 需要设计新结构 |
| **文档更新** | 文档过时 | 低成本高收益 | 需要持续维护 |
| **补充测试** | 测试缺失 | 防止回归 | 需要时间编写测试 |
| **标记待办** | P3低优先级 | 不影响当前开发 | 可能永远不修复 |

### 3.3 偿还后的验证

```
1. 单元测试：修改的函数/脚本是否正常工作
2. 集成测试：修改后上下游是否正常
3. 端到端测试：完整流程是否跑通
4. 回归测试：之前的bug是否复现
5. 性能测试：修改后性能是否下降
```

## 四、实战的技术债案例

### 案例1：rules.py 17个无用函数

**问题**：rules.py有474行，其中17个函数从未被调用。

**根因**：早期开发时为了"完整性"写了很多函数，但实际工作流只用了其中一部分。多轮修改后，有些函数被替代了但没有删除。

**修复**：
1. 用grep搜索每个函数的调用方
2. 确认17个函数没有任何调用方
3. 删除无用函数，rules.py从474行降到350行
4. 回归测试：数量计算和命中核对仍然正常

**经验**：不要为了"完整性"写无用的函数，只写实际需要的。

### 案例2：16个脚本职责不清

**问题**：scripts目录有16个Python脚本，其中notify.py的功能已经合并到cloud_write.py，但notify.py文件还在。stats.py和upload_history.py都有resolve_base_token函数。

**根因**：多轮迭代中，脚本不断新增，但旧脚本没有及时清理或合并。

**修复**：
1. 绘制脚本依赖关系图
2. 识别重复功能：notify.py→cloud_write.py，stats.py的resolve_base_token→config.py
3. 删除notify.py，将stats.py的重复函数迁移到config.py
4. 更新script-reference.md
5. 回归测试：所有脚本仍然正常工作

**经验**：新增脚本时必须考虑是否与现有脚本重复，删除旧功能时必须同步删除旧脚本。

### 案例3：多个文档中部分文档从未被引用

**问题**：技能有19个references文档，但SKILL.md和脚本只引用了其中9个，10个文档从未被使用。

**根因**：早期为了"专业"加了很多文档，但SKILL.md的渐进式披露索引没有同步更新，导致文档存在但没用。

**修复**：
1. 审计每个文档的引用情况
2. 确认10项指标从未被决策树或分析引用
3. 方案A：将这10项指标纳入决策树评分（如果有价值）
4. 方案B：将这10项指标移到full层，不默认计算（如果价值不大）
5. 最终：5项纳入决策树，5项移到full层

**经验**：新增指标时必须同时更新决策树，否则就是信号孤岛。

### 案例4：文档与实际不一致

**问题**：script-reference.md列出了7个脚本，但实际scripts目录有16个脚本。SKILL.md说"7个确定性脚本"，但实际有16个。

**根因**：多轮迭代中脚本数量增加了，但文档没有同步更新。

**修复**：
1. 盘点实际scripts目录的所有脚本
2. 更新script-reference.md，列出所有脚本及其职责
3. 更新SKILL.md的版本描述
4. 建立文档更新检查清单：每次新增/删除脚本时必须同步更新文档

**经验**：文档更新必须与代码修改同步，不能"以后再补"。

## 五、技术债预防机制

### 5.1 编码规范

```
1. 单一职责：每个脚本/函数只做一件事
2. 配置外置：所有凭据/配置集中在config.py
3. 无死代码：不写确认无用的代码
4. 文档同步：代码修改时同步更新文档
5. 测试先行：新功能必须有测试用例
```

### 5.2 Code Review检查清单

```
每次修改技能后，必须检查：
  - [ ] 是否有新增的无用函数/脚本？
  - [ ] 是否有重复代码可以合并？
  - [ ] 新增指标是否同步更新了决策树？
  - [ ] 新增脚本是否同步更新了文档？
  - [ ] 是否有硬编码的凭据？
  - [ ] 修改后是否跑了端到端测试？
  - [ ] 是否有意外的副作用？
```

### 5.3 定期重构

```
频率：每10期或每月一次
内容：
  1. 技术债审计（按审计清单逐项检查）
  2. 技术债分级（P0/P1/P2/P3）
  3. 偿还优先级排序
  4. 偿还P0和P1级技术债
  5. 制定P2和P3级技术债的偿还计划
  6. 回归验证
```

## 六、检查清单：你的技能是否有技术债管理

- [ ] 是否有定期技术债审计机制？
- [ ] 是否有技术债登记表（记录所有已知技术债）？
- [ ] 技术债是否分级（P0/P1/P2/P3）？
- [ ] 是否有技术债偿还计划？
- [ ] 死代码是否定期清理？
- [ ] 重复代码是否定期合并？
- [ ] 脚本职责是否清晰（每个脚本只做一件事）？
- [ ] 指标是否都被使用（无信号孤岛）？
- [ ] 文档是否与实际代码一致？
- [ ] 配置是否外置（无硬编码凭据）？
- [ ] 是否有端到端测试（修改后回归验证）？
- [ ] Code Review是否包含技术债检查？

**0-4项**：技术债管理严重不足，技能会越来越难维护
**5-8项**：技术债管理基本完整，但可能有遗漏
**9-13项**：技术债管理完善，技能可持续维护
