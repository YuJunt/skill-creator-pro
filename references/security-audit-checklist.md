# 技能安全审计清单

> 基于Anthropic官方最佳实践 + 业界安全指南整理
> 适用于：创建新技能时的安全自查、使用第三方技能时的安全审计、技能上线前的安全评审

---

## 一、为什么技能安全审计至关重要

### 1.1 技能的安全风险

技能是agent能力的扩展，也是安全风险的入口：
- **代码执行风险**：技能里的脚本可能执行危险操作（删除文件/发送数据/修改系统）
- **数据泄露风险**：技能可能收集/发送用户数据到第三方
- **凭据泄露风险**：技能可能硬编码API key/token，或在日志中输出敏感信息
- **权限越界风险**：技能可能请求超出必要范围的权限
- **供应链风险**：第三方技能可能包含恶意代码
- **提示注入风险**：技能处理的外部内容可能包含恶意指令

### 1.2 安全审计的核心价值

1. **预防**：在技能创建/使用前发现安全问题
2. **保护**：保护用户数据/系统/凭据不被泄露或滥用
3. **信任**：经过安全审计的技能，用户可以放心使用
4. **合规**：满足数据安全/隐私保护的合规要求

## 二、安全审计8大类30项

### 类别1：代码安全（5项）

#### 1.1 无危险命令
- [ ] 脚本中没有`rm -rf /`、`dd if=`等破坏性命令
- [ ] 没有未经确认的文件删除/覆盖操作
- [ ] 没有修改系统配置/环境变量的操作
- [ ] 危险操作有确认机制（如`--yes`参数或交互确认）

#### 1.2 无命令注入
- [ ] 用户输入不直接拼接到shell命令中
- [ ] 使用参数化接口（如subprocess的list形式），不是字符串拼接
- [ ] 用户输入有校验/转义
- [ ] 没有`eval()`/`exec()`执行用户输入的代码

#### 1.3 无硬编码凭据
- [ ] API key/token/密码不硬编码在脚本里
- [ ] 凭据通过环境变量/配置文件传入
- [ ] 配置文件有`.gitignore`，不提交到版本库
- [ ] 示例代码中的凭据是占位符，不是真实值

#### 1.4 依赖安全
- [ ] 第三方库来自可信来源（PyPI官方/官方镜像）
- [ ] 第三方库版本固定（不是`latest`）
- [ ] 没有已知漏洞的依赖（可用`pip audit`检查）
- [ ] 依赖数量最小化（不引入不必要的库）

#### 1.5 错误处理安全
- [ ] 错误信息不泄露敏感信息（如完整路径/凭据/内部结构）
- [ ] 错误信息对用户友好（不是堆栈跟踪）
- [ ] 敏感操作失败时有回滚机制
- [ ] 没有静默失败（except后不pass）

---

### 类别2：数据安全（5项）

#### 2.1 数据收集最小化
- [ ] 只收集完成任务必要的数据
- [ ] 不收集与任务无关的用户信息
- [ ] 数据收集有明确说明（用户知道收集了什么）
- [ ] 没有隐藏的数据收集（如后台发送统计数据）

#### 2.2 数据存储安全
- [ ] 敏感数据（凭据/个人信息）加密存储
- [ ] 临时数据使用后清理（不长期保留）
- [ ] 数据存储在安全位置（不是/tmp或公开目录）
- [ ] 数据文件有合适的权限（不是777）

#### 2.3 数据传输安全
- [ ] 网络传输使用HTTPS（不是HTTP）
- [ ] 不向第三方发送用户数据（除非用户明确同意）
- [ ] 发送的数据有脱敏处理（不发送完整凭据/个人信息）
- [ ] 没有隐藏的网络请求（如后台遥测）

#### 2.4 数据删除
- [ ] 任务完成后，临时数据可以删除
- [ ] 用户可以请求删除其数据
- [ ] 数据删除有确认机制（防止误删）
- [ ] 删除是彻底的（不是只删引用）

#### 2.5 数据备份
- [ ] 重要数据有备份机制
- [ ] 备份数据加密存储
- [ ] 备份有访问控制（不是所有人都能读）
- [ ] 备份定期测试可恢复性

---

### 类别3：权限安全（4项）

#### 3.1 最小权限原则
- [ ] 技能只请求完成任务必要的权限
- [ ] 不请求超出范围的权限（如只读任务不请求写权限）
- [ ] 权限请求有明确说明（用户知道为什么需要这个权限）
- [ ] 高权限操作有额外确认

#### 3.2 权限隔离
- [ ] 不同功能使用不同的权限（不是一个超级权限）
- [ ] 凭据按功能隔离（不是一个key访问所有API）
- [ ] 权限可以单独撤销（撤销一个不影响其他）
- [ ] 没有共享凭据（多个用户用同一个key）

#### 3.3 访问控制
- [ ] 敏感操作有访问控制（不是所有人都能执行）
- [ ] 配置/凭据文件有访问控制（不是所有人都能读）
- [ ] API有认证/授权（不是匿名访问）
- [ ] 操作有日志记录（谁在什么时候做了什么）

#### 3.4 权限审计
- [ ] 定期审计权限使用情况（是否有滥用）
- [ ] 不再使用的权限及时撤销
- [ ] 权限变更有记录
- [ ] 异常权限使用有告警

---

### 类别4：输入安全（4项）

#### 4.1 输入校验
- [ ] 所有用户输入都有校验（类型/范围/格式）
- [ ] 非法输入有明确错误提示（不是崩溃）
- [ ] 输入长度有限制（防止溢出/拒绝服务）
- [ ] 特殊字符有转义/过滤

#### 4.2 路径安全
- [ ] 文件路径不直接使用用户输入（防止路径遍历）
- [ ] 路径有白名单/根目录限制（不能访问上级目录）
- [ ] 符号链接有处理（防止通过symlink访问受限文件）
- [ ] 临时文件使用安全的临时目录（不是当前目录）

#### 4.3 提示注入防护
- [ ] 外部内容（网页/文件/API响应）不直接作为指令执行
- [ ] 外部内容有明确的边界标记（如"以下是用户提供的内容"）
- [ ] 外部内容中的指令不执行（只作为数据处理）
- [ ] 敏感操作不基于外部内容自动执行（需要用户确认）

#### 4.4 输出编码
- [ ] 输出到shell的内容有转义（防止命令注入）
- [ ] 输出到HTML的内容有转义（防止XSS）
- [ ] 输出到JSON的内容有正确编码（防止格式错误）
- [ ] 输出不包含敏感信息（如凭据/内部路径）

---

### 类别5：网络安全（3项）

#### 5.1 安全传输
- [ ] 所有网络请求使用HTTPS（不是HTTP）
- [ ] SSL证书验证开启（不是`verify=False`）
- [ ] 不使用过时的加密协议（SSLv3/TLS1.0）
- [ ] 网络超时设置合理（防止无限等待）

#### 5.2 API安全
- [ ] API调用有认证（API key/OAuth）
- [ ] API调用有速率限制（防止被封禁/拒绝服务）
- [ ] API响应有校验（不是盲目信任）
- [ ] API错误有重试机制（指数退避，不是无限重试）

#### 5.3 网络隔离
- [ ] 不访问不可信的网络地址（如内网/本地服务）
- [ ] 网络请求有白名单（只访问可信域名）
- [ ] 不开放网络端口（技能不是服务端）
- [ ] 不代理网络流量（防止被滥用）

---

### 类别6：日志安全（3项）

#### 6.1 日志内容安全
- [ ] 日志不包含敏感信息（凭据/密码/token/个人信息）
- [ ] 敏感信息在日志中脱敏（如`key: abc***`）
- [ ] 日志不包含完整的用户输入（可能包含敏感信息）
- [ ] 错误日志不包含堆栈跟踪中的敏感信息

#### 6.2 日志存储安全
- [ ] 日志文件有合适的权限（不是所有人都能读）
- [ ] 日志存储在安全位置（不是公开目录）
- [ ] 日志有轮转机制（不无限增长）
- [ ] 日志定期清理（不长期保留）

#### 6.3 日志访问控制
- [ ] 日志不是所有人都能读
- [ ] 敏感日志有额外的访问控制
- [ ] 日志访问有记录（谁在什么时候读了什么）
- [ ] 日志不能被篡改（有完整性校验）

---

### 类别7：供应链安全（3项）

#### 7.1 来源可信
- [ ] 技能来自可信来源（官方/已知作者）
- [ ] 第三方技能有作者信息/联系方式
- [ ] 技能有版本号/更新日志
- [ ] 不使用匿名/未知来源的技能

#### 7.2 代码可审计
- [ ] 技能代码是可读的（不是混淆/加密的）
- [ ] 脚本没有隐藏的恶意代码（如后台发送数据）
- [ ] 依赖是可信的（来自官方源）
- [ ] 没有二进制文件（除非有明确说明和校验）

#### 7.3 更新安全
- [ ] 技能更新有变更说明（知道改了什么）
- [ ] 更新不会自动执行（需要用户确认）
- [ ] 更新可以回滚（出问题可以恢复）
- [ ] 更新不引入新的安全风险（更新后重新审计）

---

### 类别8：合规与隐私（3项）

#### 8.1 隐私政策
- [ ] 技能有明确的隐私说明（收集什么数据/用来做什么）
- [ ] 用户数据不用于未说明的用途
- [ ] 用户可以选择不收集数据（opt-out）
- [ ] 符合相关隐私法规（如GDPR/个人信息保护法）

#### 8.2 数据处理合规
- [ ] 个人信息处理有合法依据
- [ ] 敏感个人信息有额外保护
- [ ] 数据跨境传输有合规措施
- [ ] 数据处理有记录（可审计）

#### 8.3 用户权利
- [ ] 用户可以访问其数据
- [ ] 用户可以更正其数据
- [ ] 用户可以删除其数据
- [ ] 用户可以导出其数据

## 三、安全审计流程

### Step 1: 快速筛查（5分钟）
- 检查是否有硬编码凭据（grep搜索key/token/password）
- 检查是否有危险命令（grep搜索rm/dd/eval/exec）
- 检查是否有网络请求（grep搜索requests/urllib/http）
- 检查依赖是否可信（requirements.txt）

### Step 2: 详细审计（30分钟）
- 按8大类30项逐项检查
- 记录发现的问题（分级：高/中/低）
- 高优先级问题必须修复后才能使用

### Step 3: 渗透测试（可选，1小时）
- 尝试命令注入（输入特殊字符）
- 尝试路径遍历（输入`../`）
- 尝试提示注入（在外部内容中插入指令）
- 尝试权限越界（请求超出范围的操作）

### Step 4: 审计报告
```
安全审计报告：{技能名}
日期：{日期}
审计者：{审计者}

总体评级：安全/基本安全/不安全

问题统计：
- 高优先级：{X}个（必须修复）
- 中优先级：{Y}个（建议修复）
- 低优先级：{Z}个（可选修复）

高优先级问题：
1. {问题描述} → {修复建议}
2. ...

中优先级问题：
1. ...

低优先级问题：
1. ...

结论：{可以使用/修复后可以使用/不建议使用}
```

## 四、常见错误

### 错误1：只检查代码，不检查依赖
**症状**：脚本本身没问题，但引入的第三方库有漏洞
**修正**：依赖也要审计，用`pip audit`检查已知漏洞

### 错误2：只检查创建时，不检查更新
**症状**：创建时审计通过了，但后续更新引入了安全问题
**修正**：每次更新后重新审计，更新有变更说明

### 错误3：只检查自己的技能，不检查第三方技能
**症状**：自己的技能安全，但使用的第三方技能有恶意代码
**修正**：第三方技能使用前必须审计，来源要可信

### 错误4：安全审计太形式化，不实际测试
**症状**：按清单逐项打勾，但没有实际尝试攻击
**修正**：高风险技能要做渗透测试，实际尝试命令注入/路径遍历等

### 错误5：安全问题修复不彻底
**症状**：修复了表面问题，但根因还在（如只删了硬编码key，但新代码又硬编码了）
**修正**：修复根因，建立安全编码规范，防止再犯
