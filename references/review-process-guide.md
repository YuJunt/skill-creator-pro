# 技能规范评审完整流程

> 基于多领域技能开发实战总结 + Anthropic官方最佳实践。规范评审不是"看一眼觉得还行"，而是系统性地对照检查清单逐项核查，给出可追溯的评审结论和改进建议。
> 核心结论：**没有规范评审的技能不能发布——规范评审是发布前的最后一道质量门，确保技能符合官方规范、架构合理、内容完整、工程可靠、质量达标。**

---

## 一、为什么需要规范评审

### 1.1 规范评审的价值

| 价值 | 说明 |
|------|------|
| **质量保证** | 发布前发现问题，避免用户遇到bug |
| **规范一致** | 确保技能符合官方规范和最佳实践 |
| **可维护性** | 确保技能结构合理，后续维护成本低 |
| **可复用性** | 确保技能接口清晰，可以与其他技能组合 |
| **安全性** | 确保技能没有安全风险（硬编码凭据/恶意代码等） |
| **用户体验** | 确保技能文档清晰，用户容易上手 |

### 1.2 什么时候需要规范评审

1. **新技能发布前**：新技能第一次发布前必须做完整规范评审
2. **重大更新后**：技能有重大更新（架构重构/新增核心功能）必须重新评审
3. **定期评审**：生产级技能每季度做一次规范评审（防止技术债积累）
4. **问题修复后**：发现严重问题修复后，做针对性评审

## 二、规范评审的7个维度

### 维度1：规范层（8项，官方强制）

**检查项**：
```
1. frontmatter规范（name/description格式正确，仅使用标准字段）
2. description三要素（What/When/Differentiator，包含触发词）
3. SKILL.md <500行（超过300行考虑拆分）
4. 渐进式披露三层架构（L1元数据/L2 SKILL.md/L3 references）
5. 文件引用一级深度（不嵌套引用，大文件有目录索引）
6. 无时间敏感信息（不写"今天""最新"，版本号放末尾）
7. 术语一致（同一概念用同一词，专业术语有解释）
8. 示例具体（真实输入输出示例，覆盖正常+边界场景）
```

**评审方法**：运行`validate_skill.py`，人工抽查。

**通过标准**：8项全部达标。

---

### 维度2：架构层（6项，设计模式）

**检查项**：
```
1. 设计哲学明确（Capability/Process/混合，内容与哲学匹配）
2. 单一职责（一个技能做一件事，触发词精确，不与其他技能冲突）
3. 渐进式披露执行层（明确"什么时候读什么"，每个reference有加载条件）
4. 技能组合友好（输出结构化，接口清晰，可与其他技能组合）
5. 模块化拆分（高内聚低耦合，模块间接口清晰，每个模块有明确输入输出）
6. 编排脚本（复杂技能有统一入口管理工作流状态，多阶段管道）
```

**评审方法**：人工审查SKILL.md和目录结构，运行脚本验证。

**通过标准**：必备项（1-4）全部达标，推荐项（5-6）根据技能复杂度评估。

---

### 维度3：内容层（5项，防LLM偷懒）

**检查项**：
```
1. Gotchas驱动（具体失败模式+修正方法，≥5个，不是抽象规则）
2. 示例驱动（examples/有1-2个完整示例，覆盖完整流程）
3. 输出格式文档化（明确输出格式，简洁版+完整版，脚本输出格式有示例）
4. 自由度匹配（根据任务脆弱性调整指令严格程度，高/中/低三档）
5. 方法论知识库（references/有规则文档+方法论文档，SKILL.md明确什么时候读）
```

**评审方法**：人工审查SKILL.md/references/examples，用真实任务测试LLM行为。

**通过标准**：必备项（1-4）全部达标，推荐项（5）根据技能复杂度评估。

---

### 维度4：工程层（5项，确定性）

**检查项**：
```
1. 确定性推入代码（脆弱/重复/一致性要求高的逻辑脚本化，Bash-first prose-second）
2. 错误处理（每个脚本try-catch，不静默失败，降级机制，错误信息可定位）
3. 校验门禁（关键操作前硬校验，缺字段就报错，validator脚本独立可调用）
4. 配置中心（凭据外置，环境变量覆盖，配置概览脱敏，不硬编码真实凭据）
5. 状态管理（orchestrator管理stage状态，状态流转清晰，防止重复执行，状态持久化）
```

**评审方法**：代码审查，运行脚本测试错误处理，构造异常输入测试校验门禁。

**通过标准**：必备项（1-3）全部达标，推荐项（4-5）根据技能复杂度评估。

---

### 维度5：质量层（4项，验证）

**检查项**：
```
1. 端到端实测（真实跑通完整流程，覆盖正常+边界+异常场景，测试结果可复现）
2. 评估用例（触发评估+行为评估+质量评估，≥3个用例，有明确通过标准）
3. 规范评审（对照检查清单逐项核查，问题分级，改进建议具体可执行）
4. 多模型测试（不同模型下行为一致，不依赖特定模型特性，提示词对模型鲁棒）
```

**评审方法**：查看测试报告，运行测试用例，多模型测试（如果可能）。

**通过标准**：必备项（1-2）全部达标，推荐项（3-4）根据技能重要性评估。

---

### 维度6：进化层（4项，自进化）

**检查项**：
```
1. 自进化闭环（执行→结算→复盘→经验提取→经验库→下次参考，闭环完整）
2. 经验回流（经验写入持久化存储，有标签/置信度/适用场景/命中率，下批参考）
3. 复盘机制（固定复盘清单，逐项回答，反事实推理，置信度校准）
4. 指标监控（各方案/各方法的效果统计，数据驱动优化，异常指标告警）
```

**评审方法**：查看自进化相关脚本和文档，用历史数据测试闭环。

**通过标准**：根据技能类型评估（持续运行技能必须达标，一次性技能可豁免）。

---

### 维度7：运维层（4项，生产级）

**检查项**：
```
1. 云端持久化（关键数据云端存储，不只是本地缓存，多设备可访问）
2. 定时任务（自动执行，配置正确，失败有重试，状态可查询）
3. 通知推送（结果推送到手机端，包含关键信息，有完整报告链接）
4. 备份恢复（写入失败时本地备份，备份文件有时间戳，可手动恢复，不丢数据）
```

**评审方法**：查看运维相关配置，测试定时任务和通知推送，模拟写入失败测试备份。

**通过标准**：根据技能部署环境评估（生产级技能必须达标，本地技能可豁免）。

## 三、规范评审执行流程

### 阶段1：准备（15分钟）

```
步骤1：确认评审范围
  - 评审的技能名称和版本
  - 评审的维度（全部7个维度/特定维度）
  - 评审的重点（新功能/问题修复/定期评审）

步骤2：准备评审工具
  - validate_skill.py（规范校验）
  - audit_skill.py（深度审计）
  - 36-element-checklist.md（检查清单）
  - 测试用例（端到端实测）

步骤3：备份技能
  - 备份技能目录（防止评审过程中意外修改）
  - 记录评审前的状态（版本号/最后修改时间）
```

### 阶段2：评审执行（1-2小时）

```
步骤4：运行规范校验（维度1）
  - 运行validate_skill.py
  - 记录通过/失败的检查项
  - 人工抽查不确定的项

步骤5：架构评审（维度2）
  - 审查SKILL.md结构
  - 审查目录结构和模块划分
  - 审查设计哲学是否明确
  - 审查技能组合友好性

步骤6：内容评审（维度3）
  - 审查Gotchas是否具体
  - 审查示例是否完整
  - 审查输出格式是否文档化
  - 审查自由度匹配是否合理
  - 用真实任务测试LLM行为

步骤7：工程评审（维度4）
  - 代码审查（脚本质量/错误处理/配置管理）
  - 测试校验门禁（构造异常输入）
  - 测试错误处理（模拟失败场景）
  - 测试状态管理（重复执行/状态流转）

步骤8：质量评审（维度5）
  - 查看端到端实测报告
  - 运行评估用例
  - 检查测试覆盖率
  - 多模型测试（如果可能）

步骤9：进化评审（维度6）
  - 审查自进化闭环是否完整
  - 测试经验提取和经验库
  - 审查复盘机制
  - 审查指标监控

步骤10：运维评审（维度7）
  - 测试云端持久化
  - 测试定时任务
  - 测试通知推送
  - 测试备份恢复
```

### 阶段3：问题汇总与改进建议（30分钟）

```
步骤11：问题分类
  - 按维度分类（哪个维度发现的问题）
  - 按严重程度分类（严重/高/中/低）
  - 按类型分类（规范问题/架构问题/内容问题/工程问题/质量问题）

步骤12：优先级排序
  - 严重问题：必须修复，不修复不能发布
  - 高优先级问题：建议修复，发布前最好修复
  - 中优先级问题：择机修复，发布后第一个迭代修复
  - 低优先级问题：可选修复，有时间再修

步骤13：改进建议
  - 每个问题给出具体的改进建议（不是"需要改进"，而是"怎么改"）
  - 给出改进的参考（相关文档/最佳实践/示例）
  - 估计改进的工作量（小时/天）

步骤14：生成评审报告
  - 汇总各维度评审结果
  - 列出问题清单和改进建议
  - 给出最终评审结论
  - 给出后续行动计划
```

## 五、常见误区

### 误区1："规范评审就是走个过场"
**事实**：规范评审是发布前的最后一道质量门，必须认真对待。走过场的评审会让严重问题流到用户手中。

### 误区2："只评审SKILL.md就够了"
**事实**：SKILL.md只是技能的入口，规范评审必须覆盖7个维度，包括脚本/references/examples/测试等。

### 误区3："发现问题太多，评审通不过就不发布了"
**事实**：评审的目的是发现问题，不是卡发布。发现问题后按优先级修复，严重问题修复后就可以发布，中低优先级问题可以后续迭代修复。

### 误区4："评审完就结束了"
**事实**：评审结束后必须跟踪改进情况，确保问题被修复。可以用问题登记表跟踪每个问题的状态。

### 误区5："自己评审自己的技能就行"
**事实**：自己评审自己的技能会有盲区（"我知道应该怎么用"会影响判断）。最好让其他人（或模拟其他人视角）来评审。

## 六、检查清单：你的规范评审是否完整

- [ ] 是否覆盖全部7个维度？
- [ ] 规范层是否有8项检查？
- [ ] 架构层是否有6项检查？
- [ ] 内容层是否有5项检查？
- [ ] 工程层是否有5项检查？
- [ ] 质量层是否有4项检查？
- [ ] 进化层是否有4项检查？
- [ ] 运维层是否有4项检查？
- [ ] 问题是否有分类（严重/高/中/低）？
- [ ] 每个问题是否有具体的改进建议？
- [ ] 是否有最终评审结论（通过/有条件通过/不通过）？
- [ ] 是否有后续行动计划？
- [ ] 是否跟踪改进情况？

**0-4项**：规范评审严重不足，技能质量没有保障
**5-9项**：规范评审基本完整，但有遗漏维度
**10-13项**：规范评审完整，技能质量有保障
