# 技能架构模式参考

> 基于业界最佳实践整理的技能架构模式，供新建/优化技能时参考

---

## 模式一：渐进式披露三层架构

### 适用场景
所有技能，尤其是内容较多的技能

### 架构图
```
L1: Metadata（始终加载，~100词）
    └── frontmatter: name + description
         ↓ 触发后加载
L2: Instructions（触发后加载，<5000词）
    └── SKILL.md body: 工作流 + Gotchas + 快速开始
         ↓ 按需加载
L3: Resources（按需加载，无上限）
    ├── references/  文档/方法论/规则
    ├── scripts/     可执行代码
    └── assets/      模板/图片/字体
```

### 关键原则
- L1只放触发信息，不放使用说明
- L2只放核心工作流，不放详细参考
- L3按需加载，SKILL.md里明确说明"什么时候读什么"
- 文件引用一级深度，不嵌套

### 反面教材
```
# 错误：所有内容都在SKILL.md里
SKILL.md（2000行）
├── 1000行规则说明
├── 500行方法论
├── 300行示例
└── 200行工作流
```

### 正确做法
```
# 正确：三层拆分
SKILL.md（150行）
├── 触发路由
├── Gotchas（10个）
├── 快速开始
└── 渐进式披露索引
references/
├── rules.md（规则）
├── methods.md（方法论）
└── 自进化文档-evolution.md（自进化）
examples/
└── example-full-analysis.md（完整示例）
```

## 模式二：触发路由（Intent Routing）

### 适用场景
支持多种模式/方案类型/路径的技能

### 架构图
```
用户输入
    ↓
Step 0: 意图分类（LLM判断模式）
    ↓
Step 1: 路由决策（选择对应路径）
    ↓
Step 2: 上下文加载（渐进式披露）
    ↓
Step 3: 执行（在选定路径上执行）
    ↓
Step 4: 验证（校验该模式的输出要求）
```

### 路由输出格式
```
🔀 路由: {模式}｜对象: {XXXX}｜管道: {几段}｜原因: {一句话}
```

### 路由表设计
| 模式 | 触发词 | 管道 | 必读文档 | 输出详略 |
|------|--------|------|----------|----------|
| 模式A | "关键词1""关键词2" | 流程A | doc-a.md | 完整版 |
| 模式B | "关键词3" | 流程B | doc-b.md | 极简版 |
| ... | ... | ... | ... | ... |

### 硬门禁校验
在关键步骤前校验路由模式字段：
```python
mandatory_checks = [
    ("路由模式", "路由模式" in report, "Step0: 缺路由模式，没先做触发路由"),
    # ... 其他检查
]
```

### 适用案例
- 技能：完整分析/快速推荐/规则问答/结算核对/效果复盘
- 学术论文：新建/修改/润色/审稿
- 代码开发：功能开发/Bug修复/代码审查/性能优化

## 模式三：编排脚本三段式

### 适用场景
有多步骤工作流、需要状态管理的技能

### 架构图
```
create_skill.py
    ├── start（采集+计算+决策树）
    │   ├── 数据采集（data_fetcher）
    │   ├── 指标计算（indicators）
    │   └── 决策树（decision_tree）
    │   输出：mandatory_steps + must_read + candidate_numbers
    │
    ├── continue（校验+写库）
    │   ├── 硬校验（validator）
    │   ├── 写执行记录（cloud_write write-bet）
    │   └── 写分析报告（cloud_write write-report）
    │   输出：record_ids + report_written
    │
    └── settle（结算+复盘）
        ├── 命中核对（rules check）
        ├── 更新云端状态
        ├── 模拟账户更新
        └── 复盘清单输出
        输出：命中结果 + 复盘清单
```

### 状态管理
```
start → analyzing → done
  ↑                    │
  └──── 重新开始 ──────┘
```

- start后状态为analyzing
- continue后状态为done
- done状态不能再continue（需重新start）
- 状态持久化到state.json

### 关键设计
- start只做确定性计算，不做分析决策
- AI分析在start和continue之间（LLM做）
- continue硬校验AI分析是否完整
- settle自动结算，不需要AI干预

## 模式四：四方协同

### 适用场景
需要数据采集+分析决策+云端存储+平台能力的复杂技能

### 职责边界
| 角色 | 职责 | 具体工作 | 禁止 |
|------|------|----------|------|
| 技能（脚本） | 确定性计算 | 数据采集/指标计算/数量计算/命中核对/校验 | 分析决策/决策/执行方案 |
| LLM（AI） | 分析决策 | 信号诊断/方法论选择/决策/执行方案/复盘反思 | 手算指标/手算数量/确定性计算 |
| 平台 | 能力支撑 | 搜索/可视化/记忆/定时任务/云盘 | 业务逻辑/数据分析 |
| 云端（云端） | 持久化 | Base存储/Doc报告/IM通知/Wiki/ Drive备份 | 计算/分析/决策 |

### 数据流
```
技能采集数据 → LLM分析决策 → 云端持久化 → 平台通知用户
     ↑              ↑              ↑
  确定性计算     分析推理       数据存储
```

### 关键原则
- 职责分明，不可越权
- 技能只做确定性计算，所有判断由LLM做
- 关键数据必须云端持久化，不只是本地缓存
- 平台能力按需使用，不滥用

## 模式五：Gotchas驱动

### 适用场景
所有技能，尤其是LLM容易偷懒/出错的技能

### Gotcha格式
```
### N. 【坑的名称】
   - 症状：【具体表现，不是抽象描述】
   - 修正：【具体做法，可执行】
   - 原因：【为什么会出现这个坑】（可选）
```

### 反面教材（抽象规则）
```
❌ 严禁偷懒，必须认真分析每个指标
❌ 禁止跳过任何步骤
❌ 必须输出完整的分析过程
```

### 正确做法（具体Gotchas）
```
✅ 排除项冲突时必须降权，不能无视
   - 症状：kill_conflict.conflict_numbers非空，你还是照选
   - 修正：冲突的数据项降权10分，或者直接排除

✅ 连续多批同趋势时，决策树会推荐反转，但反转不一定发生
   - 症状：连续4批趋势B，决策树推荐趋势A，但实际继续趋势B
   - 修正：必须在风险提示里写"连续N批X趋势，反转不一定发生"
```

### Gotchas来源
1. 实际使用中发现的坑
2. 多轮修修补补后留下的技术债
3. LLM反复犯的错误
4. 边界场景下的异常行为

### Gotchas数量
- 简单技能：≥3个
- 中等技能：≥5个
- 复杂技能：≥10个

## 模式六：决策树+候选输出

### 适用场景
需要从多个选项中选择最优的技能（如多方案类型决策、多方案选择）

### 架构图
```
输入：指标数据
    ↓
决策树（脚本计算）
    ├── 初始化所有选项基础分
    ├── 逐步评分（每步给符合条件的选项加分）
    ├── 冲突降权（矛盾信号时降权）
    └── 排序输出
    ↓
输出：候选列表（带分数）+ 候决策码/候选方案
    ↓
LLM最终选择（结合经验/风险偏好）
```

### 关键设计
- 所有选项都纳入评分，不是只评几个
- 输出候决策码/候选方案，LLM只做最终选择
- 决策树有阈值设计说明，不是黑箱
- 评分可解释（每个选项的分数来源）

### 适用案例
- 技能：16种方案类型评分对比，输出候选指标B/候决策码
- 股票筛选：多因子评分，输出候选股票池
- 方案选择：多方案评分，输出候选方案

## 模式七：四方协同（特定领域架构）

> **注意**：这是特定领域的架构模式，主要适用于需要云端持久化、持续运行、多方协作的技能（如数据分析/量化交易/持续监控/内容生成）。普通工具型技能不需要这种架构。

### 适用场景
- 需要云端持久化（关键数据不只存本地）
- 需要持续运行（每天/每周自动执行）
- 需要多方协作（技能/LLM/平台/云端各司其职）
- 需要手机端通知（结果推送到手机）

### 架构图
```
┌─────────────────────────────────────────────────┐
│                  四方协同架构                      │
├──────────────┬──────────────────────────────────┤
│  技能（脚本）  │  确定性计算                      │
│              │  - 数据采集/指标计算/数量计算      │
│              │  - 校验门禁/状态管理/赛后结算      │
│              │  - 不做分析决策，不做数据持久化    │
├──────────────┼──────────────────────────────────┤
│  LLM（AI）   │  分析决策                        │
│              │  - 信号诊断/独立判断/决策推导      │
│              │  - 价值判定/执行决策/复盘反思      │
│              │  - 经验提取/方法论选择             │
├──────────────┼──────────────────────────────────┤
│  平台（豆包）  │  能力支撑                        │
│              │  - 会话存储/长期记忆/云盘          │
│              │  - 定时任务调度/用户交互           │
│              │  - 联网搜索/可视化                 │
├──────────────┼──────────────────────────────────┤
│  云端（云端）  │  持久化存储                      │
│              │  - Base存储（历史数据/执行记录）   │
│              │  - Doc报告（完整版分析报告）       │
│              │  - IM通知（手机端推送）            │
│              │  - Wiki/Drive备份                  │
└──────────────┴──────────────────────────────────┘
```

### 关键原则
- **职责分明**：四方各司其职，不可越权（技能不做分析决策，LLM不做确定性计算）
- **云端唯一可信**：关键数据必须写入云端，本地只作缓存
- **手机端优先**：所有内容尽可能云端化，手机端可查看
- **闭环完整**：从数据采集到分析决策到持久化到通知，形成完整闭环

### 适用案例
- 数据分析（销售/财务/运营等）：技能采集数据+计算指标，LLM做分析决策，云端做存储+通知
- 股票监控：技能采集行情+计算指标，LLM做分析决策，云端做存储+预警
- 持续监控：技能采集监控数据，LLM做异常分析，云端做存储+告警

### 不适用案例
- 单一工具包装（如PDF转换）：不需要云端持久化和持续运行
- 一次性任务（如单次文档生成）：不需要多方协作和定时任务
- 本地工具（如代码格式化）：不需要手机端通知和云端存储

## 模式选择指南

| 技能复杂度 | 推荐模式 |
|-----------|----------|
| 简单（单一步骤，<100行） | 渐进式披露 + Gotchas驱动 |
| 中等（多步骤，100-300行） | 渐进式披露 + 触发路由 + Gotchas驱动 + 示例驱动 |
| 复杂（多模式/多选项，>300行） | 渐进式披露 + 触发路由 + Gotchas驱动 + 示例驱动 + 编排脚本三段式 + 决策树+候选输出 + 校验门禁 |
| 生产级（持续运行，云端存储） | 复杂技能全部 + 自进化闭环 + 云端持久化 + 定时任务 + 通知推送 |
| 特定领域（数据分析/量化/持续监控） | 生产级全部 + 四方协同架构 |

> **注意**：四方协同是特定领域架构，不是所有复杂技能都需要。只有需要云端持久化、持续运行、多方协作的技能才需要四方协同。
