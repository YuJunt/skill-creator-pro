# 技能生命周期管理（Lifecycle）

> 基于ytrofr.github.io和dev.to实战总结。核心结论：**技能不是建完就不管了——需要定期审查，清理不再使用的技能，防止上下文膨胀。**

---

## 一、为什么需要生命周期管理

### 1.1 问题

```
随着技能积累：
  - 每个技能的description都被加载到上下文（即使没被触发）
  - 20个技能 × 100 tokens = 2000 tokens 每轮浪费
  - 旧技能从未使用，但还在加载
  - 上下文窗口被无效技能占用
```

### 1.2 生命周期阶段

```
创建 → 验证 → 活跃使用 → 维护 → 归档 → 删除
                ↑                    ↓
                └── 重新激活 ←── 归档审查
```

---

## 二、归档/删除SLA

| 未调用时间 | 行动 | 说明 |
|-----------|------|------|
| **30天** | 观察候选 | 记录使用频率，标记"可能不再需要" |
| **90天** | 归档候选 | 移到archive目录，或标记deprecated |
| **180天** | 删除候选 | 硬删除，除非有参考价值 |

**注意**：这些是SLA不是死线。每月审查一次候选，问"这个技能还有用吗？"

---

## 三、生命周期各阶段管理

### 阶段1：创建后验证（必须）
- [ ] 端到端实测通过
- [ ] 触发率≥90%
- [ ] 输出完整率=100%
- [ ] 安全扫描A级

### 阶段2：活跃使用中（持续监控）
- [ ] 使用统计正常（skill_observability.py）
- [ ] 成功率≥70%
- [ ] 无大量报错
- [ ] 模型更新后重新验证

### 阶段3：维护（定期）
- [ ] 每季度跑一次完整eval
- [ ] 检查是否有过时信息
- [ ] 检查脚本是否还能正常运行
- [ ] 检查依赖是否还兼容

### 阶段4：归档（决策）
- [ ] 90天未使用
- [ ] 归档前确认：是否有其他技能替代？
- [ ] 归档操作：移到archive/目录，SKILL.md标记"archived"
- [ ] 归档后：从活跃技能列表中移除

### 阶段5：删除（决策）
- [ ] 180天未使用
- [ ] 删除前确认：是否有参考价值？
- [ ] 删除操作：删除目录，git保留历史
- [ ] 删除后：清理registry中的引用

## 四、"技能不再需要"信号

### 4.1 退役信号

| 信号 | 说明 | 行动 |
|------|------|------|
| **基础模型已内化** | 不加载技能也能通过eval | 技能可退役 |
| **触发率持续下降** | 连续30天触发率<10% | 观察，考虑归档 |
| **成功率持续下降** | 连续20次eval通过率<30% | 修复或退役 |
| **有更好的替代** | 新技能覆盖旧技能功能 | 归档旧技能 |

### 4.2 检测方法

```
步骤1：跑当前技能的eval
步骤2：不加载技能，跑同样的eval
步骤3：对比通过率
  - 技能版通过率 - 无技能版通过率 < 10% → 技能可能不再需要
  - 技能版通过率 - 无技能版通过率 > 30% → 技能仍然有价值
```

## 五、上下文膨胀监控

### 5.1 计算方法

```
上下文膨胀量 = Σ(每个技能的description长度)

例：
  20个技能 × 平均150 tokens/description = 3000 tokens
  这些token每轮都被加载，即使没用到

优化：
  - 归档/删除未使用技能 → 减少膨胀
  - description精简到100 tokens以内 → 减少膨胀
```

### 5.2 监控指标

| 指标 | 目标 |
|------|------|
| 活跃技能数 | < 20个 |
| 总description token | < 3000 tokens |
| 未使用技能占比 | < 10% |
| 每月归档/删除数 | 1-2个（清理冗余） |
