> | 部分 | 内容 | 什么时候读 |

> | 第一部分 | 多模型测试 | 需要跨模型鲁棒性验证时 |

# 第一部分：多模型测试用例与评估方案

## 一、测试目标

| 目标 | 说明 | 通过标准 |
|------|------|---------|
| **触发率一致性** | 不同模型下，相同用户输入是否都能触发技能 | 触发率差异 < 10% |
| **路由输出率** | 技能触发后，不同模型是否都能输出路由行 | 路由输出率 > 90%（所有模型） |
| **流程完整性** | 不同模型是否都能完整执行工作流，不跳步 | 流程完成率 > 85% |
| **输出质量** | 不同模型的输出质量是否一致 | 质量评分差异 < 15% |
| **错误恢复** | 遇到错误时，不同模型是否都能正确处理 | 错误恢复率 > 80% |

---

## 二、测试维度

### 维度1：触发率测试

**测试方法**：准备20条不同风格的用户输入，在每个模型下运行，统计技能被触发的比例。

**测试用例**：

| 编号 | 用户输入 | 预期触发 | 输入风格 |
|------|---------|---------|---------|
| T1 | "帮我创建一个技能" | ✅ | 直接明确 |
| T2 | "这个技能有什么问题" | ✅ | 口语化 |
| T3 | "优化一下我的skill" | ✅ | 中英混合 |
| T4 | "帮我看看这个技能还能怎么改进" | ✅ | 长句口语 |
| T5 | "技能审计" | ✅ | 极简关键词 |
| T6 | "review my skill" | ✅ | 英文 |
| T7 | "测试一下这个技能的质量" | ✅ | 间接表达 |
| T8 | "我想做一个自定义技能" | ✅ | 意图表达 |
| T9 | "今天天气怎么样" | ❌ | 无关对话（不应触发） |
| T10 | "帮我写个prompt" | ❌ | 相关但不匹配（不应触发） |

**通过标准**：
- 应触发的用例（T1-T8）触发率 > 90%
- 不应触发的用例（T9-T10）误触发率 < 10%
- 各模型间触发率差异 < 10%

---

### 维度2：路由输出率测试

**测试方法**：技能触发后，统计模型输出中包含路由行（`🔀 路由: {模式}`）的比例。

**测试用例**：

| 编号 | 场景 | 预期路由 |
|------|------|---------|
| R1 | 用户说"帮我创建一个技能" | 🔀 路由: 新建技能 |
| R2 | 用户说"优化一下这个技能" | 🔀 路由: 优化技能 |
| R3 | 用户说"评审一下这个技能" | 🔀 路由: 深度评审 |
| R4 | 用户说"测试一下这个技能" | 🔀 路由: 端到端测试 |
| R5 | 用户说"继续"（上一轮已触发技能） | 应保持路由（会话保持） |
| R6 | 用户说"好的"（上一轮已触发技能） | 应保持路由（会话保持） |

**通过标准**：
- 路由行输出率 > 90%（所有模型）
- 路由模式选择正确率 > 85%
- 长对话（R5/R6）路由保持率 > 70%
- 各模型间路由输出率差异 < 10%

---

### 维度3：流程完整性测试

**测试方法**：统计模型是否完整执行工作流的所有步骤，不跳步、不偷懒。

**optimize模式完整流程（4步）**：
1. ✅ 规范校验（validate_skill.py）
2. ✅ 深度审计（audit_skill.py）
3. ✅ 安全扫描（security_scan.py）
4. ✅ 输出校验（output_validator.py）

**测试用例**：

| 编号 | 场景 | 预期步骤数 |
|------|------|-----------|
| F1 | 完整优化流程 | 4步全部执行 |
| F2 | 完整评审流程 | 3步全部执行 |
| F3 | 完整测试流程 | 包含脚本冒烟测试 |
| F4 | 用户催促"快点" | 仍应执行所有步骤（不跳步） |
| F5 | 用户说"简单点" | 仍应执行核心步骤（不少于3步） |

**通过标准**：
- 流程完成率 > 85%（所有模型）
- 核心步骤（规范校验+输出校验）执行率 100%
- 各模型间流程完成率差异 < 15%

---

### 维度4：输出质量测试

**测试方法**：对模型的输出进行质量评分（1-10分），评估内容完整性、准确性、专业性。

**评分维度**：

| 维度 | 权重 | 评分标准 |
|------|------|---------|
| **内容完整性** | 30% | 是否包含所有必需字段（结论/方案/理由/风险提示） |
| **准确性** | 25% | 分析结论是否正确，是否有事实错误 |
| **专业性** | 20% | 是否引用了方法论/最佳实践，术语使用是否准确 |
| **格式规范性** | 15% | 输出格式是否符合模板要求，路由行是否正确 |
| **可操作性** | 10% | 建议是否具体可执行，不是空泛的"需要改进" |

**通过标准**：
- 平均质量评分 > 7分（所有模型）
- 各模型间质量评分差异 < 15%
- 无严重事实错误（0分项）

---

### 维度5：错误恢复测试

**测试方法**：构造异常场景，测试模型是否能正确识别错误并恢复。

**测试用例**：

| 编号 | 异常场景 | 预期行为 |
|------|---------|---------|
| E1 | 技能目录不存在 | 明确报错，不继续执行 |
| E2 | SKILL.md格式错误 | 规范校验发现问题，提示修复 |
| E3 | 安全扫描发现高风险 | 中止流程，提示必须修复 |
| E4 | 输出校验失败 | 提示具体问题，要求修复后重新运行 |
| E5 | 脚本运行超时 | 提示超时，建议检查环境 |

**通过标准**：
- 错误识别率 > 90%（所有模型）
- 错误恢复率 > 80%（能给出正确的修复建议）
- 各模型间错误处理差异 < 15%

## 三、执行方法

### 3.1 测试环境准备

```bash
# 1. 准备测试用的技能目录
mkdir -p /tmp/test-skill
python3 scripts/init_skill_pro.py test-skill --path /tmp --philosophy mixed

# 2. 准备测试输入列表（见上文测试用例）
# 3. 在每个模型下运行相同的测试用例
# 4. 记录结果并对比
```

### 3.2 结果记录模板

```markdown
## 多模型测试结果对比

| 测试维度 | GPT-4 | Claude 3 | Gemini | 豆包 | 差异 |
|---------|-------|----------|--------|------|------|
| 触发率 | 95% | 90% | 85% | 92% | 10% |
| 路由输出率 | 95% | 85% | 80% | 90% | 15% |
| 流程完成率 | 90% | 80% | 75% | 85% | 15% |
| 输出质量 | 8.5 | 7.5 | 7.0 | 8.0 | 1.5 |
| 错误恢复率 | 90% | 80% | 75% | 85% | 15% |

## 发现的模型依赖问题

1. [问题描述] - 影响模型：[模型列表] - 严重度：[高/中/低]
2. ...

## 改进建议

1. [具体改进建议]
2. ...
```

### 3.3 问题分类与处理

| 问题类型 | 处理方式 |
|---------|---------|
| **某模型触发率低** | 优化description，增加该模型擅长识别的触发词 |
| **某模型路由输出率低** | 强化路由行指令，增加示例，降低格式复杂度 |
| **某模型跳步** | 增加硬门禁（脚本校验），强化"不允许跳过"指令 |
| **某模型输出质量低** | 增加输出模板和示例，明确质量标准 |
| **某模型错误处理差** | 增加错误处理指南，强化"遇到错误必须报错"指令 |

## 四、当前技能的多模型鲁棒性设计

skill-creator-pro 已经采用了以下多模型鲁棒性设计：

| 设计 | 作用 | 覆盖维度 |
|------|------|---------|
| **P0扩大触发范围** | 20+口语化触发场景，不依赖精确匹配 | 触发率 |

| **4步硬门禁校验** | 规范/审计/安全/输出，脚本校验不通过就中止 | 流程完整性 |
| **command参数required=True** | 不传模式脚本直接报错，强制模型先确定模式 | 流程完整性 |
| **错误处理友好** | 所有脚本对异常输入明确报错返回码1 | 错误恢复 |

# 第二部分：触发路由与must_read专项测试用例

## 一、测试目标

### 1.1 触发路由测试

验证技能是否能根据用户输入正确路由到4种模式之一，并且路由输出格式正确。

### 1.2 must_read测试

验证路由确定后，LLM是否读取了对应模式的must_read文档，并且在输出中引用了文档的具体内容。

### 1.3 强制执行规则测试

验证5条强制执行规则是否有效，违反规则时是否被识别和阻止。

| ER-014 | create_skill.py校验失败但跳过继续 | 输出被识别为无效 | 校验失败跳过=无效 |
| ER-015 | output_validator.py校验失败但绕过 | 输出被识别为无效 | 校验失败绕过=无效 |
| ER-016 | 校验失败后修复问题重新运行 | 输出有效 | 修复后重新校验通过=有效 |

## 五、测试执行方法

### 5.1 手动测试流程

```
步骤1：准备测试用例清单（本文档）
步骤2：逐个输入测试用例，观察LLM行为
步骤3：记录实际输出（路由声明/must_read引用/脚本运行情况）
步骤4：对照通过标准，标记通过/失败
步骤5：汇总测试结果，生成测试报告
```

### 5.2 自动化测试辅助

```bash
# 1. 验证脚本可运行
python3 scripts/create_skill.py review <skill-path>
python3 scripts/output_validator.py <skill-path>

# 2. 验证路由声明格式（检查输出中是否包含路由声明）
# 手动检查：LLM输出的第一条是否是 "🔀 路由: ..."

# 3. 验证must_read引用（检查输出中是否引用了文档具体内容）
# 手动检查：输出中是否有 "references/xxx.md" 的具体章节引用

# 4. 验证编排脚本运行（检查是否有脚本运行记录）
# 手动检查：输出中是否有 create_skill.py 和 output_validator.py 的运行结果
```

### 5.3 测试环境要求

- 使用真实的LLM实例测试（不是模拟）
- 每个测试用例独立运行（不共享上下文）
- 记录完整的输入输出（用于后续分析）
- 测试至少运行2轮（验证一致性）

## 六、通过标准

### 6.1 触发路由测试

| 指标 | 通过标准 |
|------|---------|
| 模式匹配准确率 | ≥ 90%（18/20用例通过） |
| 不触发准确率 | 100%（4/4用例不触发） |
| 路由格式正确率 | 100%（4/4用例格式正确） |

### 6.2 must_read测试

| 指标 | 通过标准 |
|------|---------|
| must_read文档读取率 | ≥ 90%（15/16用例读取） |
| must_read引用质量合格率 | ≥ 85%（3/4用例有具体引用） |
| 脚本运行率 | 100%（所有模式都运行了编排脚本和输出校验） |

### 6.3 强制执行规则测试

| 指标 | 通过标准 |
|------|---------|
| 规则识别率 | ≥ 90%（15/16违反场景被识别） |
| 规则阻止率 | ≥ 85%（14/16违反场景被阻止） |
| 修复后通过率 | 100%（修复后重新校验通过） |

### 6.4 总体通过标准

| 等级 | 通过率 | 说明 |
|------|--------|------|
| 优秀 | ≥ 95% | 触发路由和must_read机制完全有效 |
| 良好 | 85-94% | 核心机制有效，少量边缘场景需优化 |
| 合格 | 75-84% | 基本有效，有明显短板需修复 |
| 不合格 | < 75% | 机制无效，需大幅重构 |

### 6.5 技能质量最终验证（必须）

触发路由/must_read/强制执行规则测试通过只是手段，最终必须验证"创建出的技能质量"：

| 验证项 | 验证方法 | 通过标准 |
|--------|---------|---------|
| 规范符合性 | 运行validate_skill.py | 0高优先级问题 |
| 深度审计 | 运行audit_skill.py | 必备层20项全部达标 |
| 输出校验 | 运行output_validator.py | 0个必须修复的问题 |
| 端到端测试 | 真实跑通创建出的技能流程 | 技能能正常触发和执行 |
| 用户需求匹配 | 对比创建出的技能与用户原始需求 | 核心需求全部满足 |

**注意**：即使触发路由/must_read/强制执行规则测试全部通过，如果创建出的技能质量不达标，仍然视为测试失败。机制有效是必要条件，技能质量达标是充分条件。
