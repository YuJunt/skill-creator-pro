# 技能创建最佳实践

> 基于Anthropic官方最佳实践 + 多领域技能开发实战总结。这些是创建专业级技能时必须遵循的原则和流程。
> 核心结论：**技能创建不是写个SKILL.md就完事，而是遵循一套经过验证的最佳实践，确保技能规范、专业、可维护。**

---

## 一、默认创建位置（环境自适应）

除非用户明确指定其他位置，技能必须创建在已有的 `workspace/.user_skills` 目录内。`init_skill_pro.py` 会自动解析该目录（从环境变量、常见路径、当前目录向上查找），不需要手动指定 `--path`。

### 规则

1. 仅当用户明确要求时才使用其他位置
2. 否则自动解析并使用现有的 `workspace/.user_skills` 目录
3. 无法自动解析时，提示用户手动指定 `--path`

### 为什么重要

- 技能必须放在系统能识别的目录才能被加载
- 不同环境的路径可能不同（Linux/macOS/Windows），不能硬编码
- 自动解析避免了用户手动输入路径的错误

---

## 二、网站内容收集默认使用 Browser Use

当创建用于从网站或Web应用收集信息的技能时，Browser Use是默认执行路径。包括：搜索、浏览订阅源、打开帖子、读取评论、收集用户反馈、检查产品提及、从网站提取可见内容等。

### 不要做什么

**不要**默认将这些任务框架为Python爬虫、scraper或网站API实现任务。仅当用户明确要求基于爬虫/API的技能，或浏览器操作不足以满足明确要求时，才创建Python爬虫脚本。

### 为什么Browser Use是默认

- 浏览器操作更通用，不需要逆向分析网站API
- 浏览器操作更稳定，网站API经常变化
- 浏览器操作可以处理需要登录/交互的场景
- Python脚本仍然适用于浏览器收集数据后的确定性后处理（去重、分类、格式化、报告生成）

## 三、三种模式选择指南

创建技能的第一步是选择合适的设计哲学（模式）。选择错误会导致过度设计或功能不足。

### 3.1 三种模式对比

| 维度 | Mixed（混合型） | Process（方法论型） | Capability（工具包装型） |
|------|----------------|-------------------|------------------------|
| **核心定位** | 完整工程化技能 | 流程驱动技能 | 简洁工具技能 |
| **适用场景** | 分析/决策/复杂工作流 | 方法论/检查清单/审批流程 | 简单工具/命令包装/格式转换 |
| **脚本数量** | 3个（main+orchestrator+validator） | 2个（orchestrator+validator） | 1个（main） |
| **编排脚本** | ✅ 多阶段管道 | ✅ 多阶段管道 | ❌ 单命令调用 |
| **校验脚本** | ✅ 硬门禁 | ✅ 硬门禁 | ❌ 错误处理在脚本内 |
| **references** | 2个（最佳实践+评估用例） | 3个（工作流指南+检查清单+评估用例） | 1个（评估用例） |
| **SKILL.md行数** | ~240行 | ~260行 | ~180行 |
| **文件总数** | 8个 | 8个 | 6个 |
| **初始审计分** | 28/36 | 26/36 | 22/36 |
| **必备层** | 20/20 | 20/20 | 20/20 |

### 3.2 模式选择决策树

```
你的技能是否有明确的多步骤工作流？
├── 是 → 工作流是否需要编排脚本强制顺序（防止跳步）？
│   ├── 是 → 工作流是否需要核心工具脚本（数据处理/计算/转换）？
│   │   ├── 是 → 选择Mixed模式（完整工程化）
│   │   └── 否 → 选择Process模式（方法论驱动）
│   └── 否 → 选择Process模式（方法论驱动，编排脚本可选）
└── 否 → 你的技能是否主要是单命令调用（输入→处理→输出）？
    ├── 是 → 选择Capability模式（简洁高效）
    └── 否 → 选择Mixed模式（最通用，后续可调整）
```

### 3.3 典型场景示例

| 场景 | 推荐模式 | 原因 |
|------|---------|------|
| 数据分析技能（采集→清洗→分析→报告） | Mixed | 多步骤工作流+核心计算脚本+需要校验 |
| 代码审查技能（检查清单→逐项审查→报告） | Process | 流程驱动+检查清单+需要编排防跳步 |
| PDF转换技能（输入PDF→输出图片） | Capability | 单命令调用+不需要编排 |
| 项目管理技能（创建→分配→跟踪→结算） | Mixed | 复杂工作流+状态管理+需要编排 |
| 文档生成技能（模板→填充→输出） | Capability | 简单工具+核心脚本即可 |
| 审批流程技能（申请→审核→批准→归档） | Process | 流程驱动+检查清单+需要编排 |

### 3.4 模式选择常见误区

**误区1："Mixed模式功能最全，所有技能都选Mixed"**
- 事实：简单工具选Mixed会过度设计，3个脚本中2个永远不用，增加维护成本
- 正确：根据技能复杂度选择，简单工具选Capability

**误区2："Capability模式最简单，所有技能都选Capability"**
- 事实：复杂工作流选Capability会缺少编排和校验，LLM容易跳步偷懒
- 正确：多步骤工作流必须选Mixed或Process

**误区3："模式选了就不能改"**
- 事实：创建后可以自由添加/删除脚本和文档，模式只是初始配置
- 正确：先选最接近的模式，创建后根据实际需求调整

### 3.5 不确定时的选择

**如果不确定选什么模式，按以下优先级选择：**

1. **能确定是简单工具** → 选Capability
2. **能确定是流程/方法论** → 选Process
3. **不确定/复杂/可能扩展** → 选Mixed（最通用，后续可精简）

**Mixed模式是最安全的选择**，因为它包含最完整的工程化配套，后续可以根据实际需求删除不需要的脚本。

## 四、不应该包含什么

技能只应包含直接支持其功能的必要文件。**禁止**创建额外的文档或辅助文件，包括：

- `README.md`
- `INSTALLATION_GUIDE.md`
- `QUICK_REFERENCE.md`
- `CHANGELOG.md`
- 其他与技能功能无关的辅助文档

### 为什么禁止

- 技能应只包含AI agent完成手头工作所需的信息
- 创建额外的文档文件只会增加混乱和上下文负担
- SKILL.md已经是技能的入口和说明，不需要额外的README
- 版本信息放在SKILL.md末尾的版本区即可，不需要CHANGELOG

## 五、迭代流程（6步）

技能创建不是一次性完成的，需要持续迭代：

### 核心原则：每阶段必须实测验证通过才能继续

**这是防止技术债积累的最重要规则。** 多轮修修补补后，技能会积累大量未验证的改动，导致"看起来改了但实际没生效"或"改了A坏了B"的问题。

**强制执行规则：**
1. **分阶段执行**：将优化任务按优先级分为P0/P1/P2/P3，每个优先级为一个阶段
2. **每阶段验证**：每个阶段的所有任务完成后，必须运行完整的实测验证（语法检查+规范校验+深度审计+端到端实测）
3. **验证通过才能继续**：只有当前阶段的所有验证项全部通过，才能进入下一阶段
4. **验证不通过必须修复**：如果验证发现问题，必须在当前阶段修复，不能带着问题进入下一阶段
5. **记录验证结果**：每个阶段的验证结果必须记录（通过/不通过/发现的问题/修复情况）

**验证清单（每阶段必须全部通过）：**
- [ ] 所有修改过的脚本语法检查通过（`python3 -m py_compile`）
- [ ] 规范校验无高优先级/中优先级问题（`validate_skill.py`）
- [ ] 深度审计分数不低于优化前（`audit_skill.py`）
- [ ] 端到端实测成功（核心流程能正常跑通）
- [ ] 修改的功能点单独验证（确认改动确实生效）

---

### 第1步：理解技能

通过具体示例明确技能的使用模式和功能范围。

- 收集用户的使用场景和具体示例
- 明确技能的触发词和边界
- 确定技能的设计哲学（Capability/Process/Mixed）

### 第2步：规划可复用内容

分析每个示例，确定需要哪些 scripts/references/assets。

- 识别重复出现的操作 → 脚本化
- 识别需要参考的知识 → references文档
- 识别输出中使用的资源 → assets文件

### 第3步：初始化技能

运行 `init_skill_pro.py` 生成专业模板。

- 选择设计哲学（capability/process/mixed）
- 自动创建目录结构和示例文件
- 自动生成SKILL.md模板

### 第4步：编辑技能

实现资源、编写SKILL.md、替换TODO。

- 编写scripts/中的脚本
- 编写references/中的文档
- 编写examples/中的示例
- 完善SKILL.md的内容

### 第5步：最终化技能目录

确认结构、删除占位文件、运行脚本测试。

- 删除不需要的示例文件
- 运行所有脚本测试
- 运行规范校验和深度审计
- 端到端实测验证

### 第6步：迭代优化

在真实任务中使用，发现问题，持续优化。

- 收集使用中的问题和反馈
- 定期技术债审计
- 持续优化决策树和方法论
- 版本更新记录

## 六、检查清单：你的技能创建是否遵循最佳实践

- [ ] 技能是否创建在 `workspace/.user_skills` 目录内？
- [ ] 网站内容收集技能是否默认使用Browser Use？
- [ ] 是否没有创建README/CHANGELOG等额外文档？
- [ ] 是否遵循了6步迭代流程？
- [ ] 每个脚本是否都经过实际运行测试？
- [ ] 是否运行了规范校验和深度审计？
- [ ] 是否做了端到端实测？
- [ ] 多阶段优化时，是否每阶段都做了实测验证并通过后才继续？

**0-4项**：最佳实践遵循不足，技能质量没有保障
**5-6项**：基本遵循最佳实践，有少量遗漏
**7-8项**：完整遵循最佳实践，技能质量有保障
