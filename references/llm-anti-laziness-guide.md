# LLM偷懒系统性对抗策略指南

> 基于多个技能（数据分析/内容生成/工具包装/决策支持等）多轮开发实战总结。这是技能开发中**最核心、最容易被忽视**的经验。
> 核心结论：**抽象约束管不住LLM偷懒，必须用工程手段强制流程+硬门禁+候选输出+可验证输出。**

---

## 一、问题本质：为什么LLM会偷懒

### 1.1 LLM偷懒的5种表现形式

| 表现 | 症状 | 技能创建案例 |
|------|------|------------|
| **跳步** | 跳过工作流中的某些步骤，直接给结论 | 跳过规范校验和深度审计，直接交付技能 |
| **浅用** | 只用到技能10-20%的能力，大量脚本/文档不用 | 19个references文档只读了2个，5个脚本只用了init_skill_pro.py |
| **套模板** | 每次输出格式一样，内容换汤不换药 | 连续多次创建的技能结构一模一样，不随用户需求变化 |
| **假满足** | 表面满足约束，实际偷工减料 | 写了"已运行所有校验"但实际只运行了init，没运行validate和audit |
| **绕流程** | 不按编排脚本的流程走，自己发明捷径 | 跳过create_skill.py，直接手动创建目录结构和SKILL.md |

### 1.2 为什么抽象约束无效

```
❌ 无效的约束（实战验证过，全部无效）：
  - "严禁偷懒，必须认真分析每个数据源"
  - "禁止跳过任何步骤"
  - "必须输出完整的分析过程"
  - "所有输出格式都必须逐一支持"
  - "必须利用技能的全部能力"

为什么无效：
  1. LLM没有"认真"的概念，只有"输出符合约束的文本"
  2. 抽象约束无法验证——LLM说"我分析了10个接口"，你无法证明它没分析
  3. 上下文窗口有限，LLM倾向于用最少的token完成任务
  4. 没有即时反馈——偷懒不会被立即惩罚
```

## 二、五层对抗体系（从弱到强）

### 第1层：Gotchas驱动（弱）

**原理**：用具体的失败模式+修正方法，代替抽象规则。

**效果**：能减少30%的偷懒，但无法根除。LLM可能记住Gotchas但仍然犯。

**写法**：
```
❌ 错误写法（抽象）：
  "必须认真分析所有数据源"

✅ 正确写法（具体）：
  "输入数据为空时必须报错——症状：data是空数组，你还是输出了分析结果；
   修正：先校验输入数据非空，为空就报错并提示用户提供有效数据"
```

### 第2层：编排脚本强制流程（中）

**原理**：用脚本把工作流拆成固定阶段，LLM必须按阶段走，不能跳步。

**通用的三段式管道**：
```
start（脚本做）→ AI分析（LLM做）→ continue（脚本校验+持久化）→ settle（脚本结算复盘）
     ↓                    ↓                    ↓
  采集数据+计算指标    读指标→决策→写方案    硬校验必填字段，缺就报错
  输出mandatory_steps  必须按mandatory_steps  写云端数据库
  输出must_read        逐项完成
  输出candidate_outputs
```

**关键设计**：
- start输出`mandatory_steps`：告诉LLM本批必须完成哪些分析步骤
- start输出`must_read`：告诉LLM本批必须读哪些参考文档
- continue硬校验：缺路由模式/缺摘要/缺方法论/缺推荐结果/缺置信度/缺决策依据，任何一项缺失就报错
- 状态管理：start→analyzing→done，done状态不能再continue

**效果**：能减少60%的跳步和绕流程。但LLM可能在AI分析阶段仍然浅用功能。

### 第3层：硬门禁校验（中强）

**原理**：在关键节点用脚本校验输出的完整性和正确性，不通过就不让过。

**通用的校验层级**：
```
Layer 1: 规范校验（validate_skill.py）
  - frontmatter规范、SKILL.md行数、目录结构

Layer 2: 业务校验（validator.py）
  - 输出格式合法、数据项无重复、必填字段非空、数值范围正确

Layer 3: 流程完整性校验（orchestrator continue）
  - 路由模式/摘要/方法论/推荐结果/置信度/决策依据，6项全有才放行

Layer 4: 跨模块一致性校验
  - 输入参数必须与输出格式匹配
  - 数据校验结果必须与后续处理逻辑一致
  - 错误处理必须覆盖所有异常分支
```

**关键原则**：
- 校验只检查"有没有"，不检查"好不好"——后者需要LLM-as-Judge
- 错误信息必须明确指出缺什么，不能只说"校验失败"
- 校验失败必须阻断流程，不能警告后继续

**效果**：能减少80%的偷工减料。但无法检测"假满足"（LLM写了假的分析内容）。

### 第4层：决策树+候选输出（强）

**原理**：把多选项的评分和候选生成全部脚本化，LLM只做最终选择，不做确定性计算。

**通用的决策树设计**：
```
输入：多项指标（脚本计算）
    ↓
决策树（脚本评分）：
  - 初始化所有候选选项基础分
  - 多步逐步评分（数据特征/集中度/确定性/信号强度/预算/高级指标）
  - 冲突信号降权
  - 排序输出
    ↓
输出：候选列表（所有选项带分数）+ 候选参数/候选配置/候选方案
    ↓
LLM最终选择：结合经验/风险偏好，从候选中选最优
```

**为什么能对抗偷懒**：
1. LLM不需要"分析所有选项"——脚本已经评完了，LLM只需要看候选列表
2. LLM不需要"计算所有指标"——脚本已经算完了，LLM只需要读结果
3. 候选参数是脚本生成的，LLM不能凭感觉给结果
4. 评分可解释——每个选项的分数来源清晰

**效果**：能减少90%的浅用和套模板。LLM的工作从"从零分析"变成"从候选中选择"，难度大幅降低。

### 第5层：可验证输出+事后审计（最强）

**原理**：让LLM的输出可被脚本验证，事后用脚本审计是否真的做了分析。

**通用的可验证输出设计**：
```
LLM输出必须包含：
  1. 路由模式（可验证：是否在预设模式中）
  2. 引用的具体指标值（可验证：是否与start输出的指标一致）
  3. 方法论引用（可验证：是否引用了方法论文档的具体章节）
  4. 决策依据（可验证：是否基于具体指标，而不是"感觉"）
  5. 置信度+不确定性来源（可验证：是否量化）

事后审计：
  - 对比LLM引用的指标值与脚本计算的指标值
  - 检查LLM是否引用了start输出的must_read文档
  - 检查推荐结果是否在决策树候选范围内
  - 统计各功能的引用率，识别"从未被使用的功能"
```

**效果**：能减少95%的假满足。LLM知道输出会被审计，就不敢编造分析内容。

## 三、对抗策略选择矩阵

| 技能复杂度 | 推荐对抗层级 | 预期偷懒减少率 |
|-----------|------------|--------------|
| 简单（单一步骤） | 第1层 Gotchas | 30% |
| 中等（多步骤） | 第1+2层 Gotchas+编排 | 60% |
| 复杂（多模式/多选项） | 第1-4层 全部 | 90% |
| 生产级（持续运行） | 第1-5层 全部+事后审计 | 95% |

## 四、通用偷懒案例与解决方案

### 案例1：连续多批输出结果一模一样

**症状**：定时任务每天跑，但输出结果和前一天完全一样，不像深度分析。

**根因**：LLM在AI分析阶段没有真正读指标，直接复用了上一批的分析结果。

**解决方案**：
1. start输出`latest_batch`和`latest_data`，LLM必须引用最新批次号
2. continue校验输出结果是否与决策树候选参数一致
3. 决策树候选参数基于最新数据动态生成，每批都不一样

### 案例2：大量功能只用了少数几个

**症状**：LLM输出的分析只提到基础数据校验、格式转换，其他高级功能从未被引用。

**根因**：渐进式披露只加载core层（基础功能），extended/full层LLM不会主动加载。

**解决方案**：
1. start输出`must_read`，告诉LLM本批必须读哪些扩展功能文档
2. 决策树自动使用高级功能（复杂校验/智能推荐/异常检测等），不需要LLM手动读
3. 候选参数基于高级功能生成，LLM间接使用了所有功能

### 案例3：只输出一种格式，不对比其他选项

**症状**：永远只输出JSON格式，不支持CSV/PDF/Markdown等其他格式。

**根因**：决策树原来所有格式基础分都是50分，JSON因为最常用而排第一。

**解决方案**：
1. 决策树评分机制优化：常用格式基础分55分，冷门格式50分
2. 场景判断加入用户需求/数据量/下游系统加分
3. 输出所有格式的完整候选排名，LLM可以看到所有选项
4. 优化后CSV从第3名升到第1名，PDF排第二

### 案例4：LLM跳过编排脚本，直接手写分析

**症状**：LLM不运行create_skill.py start，直接凭感觉写分析报告。

**根因**：SKILL.md没有强制要求必须用编排脚本，LLM觉得"直接写更快"。

**解决方案**：
1. SKILL.md开头写死："必须用create_skill.py三段式管道，禁止直接凭感觉分析"
2. continue阶段校验：没有start的state文件就报错
3. Gotchas里明确写："跳过编排脚本=输出错误结果"

## 五、常见误区

### 误区1："加更多的约束就能防止偷懒"
**事实**：约束越多，LLM越容易表面满足实际套模板。约束必须是可验证的。

### 误区2："渐进式披露能解决所有问题"
**事实**：渐进式披露只解决上下文效率问题，不解决LLM偷懒问题。extended/full层LLM不会主动加载，必须用must_read强制。

### 误区3："校验门禁能检测所有偷懒"
**事实**：校验只检查"有没有"，不检查"好不好"。LLM可以编造假的分析内容通过校验。需要可验证输出+事后审计。

### 误区4："LLM能力越强越不会偷懒"
**事实**：偷懒与能力无关，与任务设计有关。任务设计得好，弱模型也能完整执行；任务设计得差，强模型也会偷懒。

## 六、检查清单：你的技能是否容易被LLM偷懒

- [ ] 工作流是否有编排脚本强制流程？
- [ ] 关键节点是否有硬门禁校验？
- [ ] 多选项是否有决策树脚本生成候选？
- [ ] LLM的输出是否可被脚本验证？
- [ ] 是否有事后审计机制？
- [ ] Gotchas是否是具体的失败模式+修正方法？
- [ ] start是否输出mandatory_steps和must_read？
- [ ] 候选参数是否由脚本生成而非LLM凭感觉？
- [ ] 评分是否可解释（每个选项的分数来源）？

**0-3项**：高风险，LLM大概率偷懒
**4-6项**：中风险，部分场景会偷懒
**7-10项**：低风险，偷懒空间很小
