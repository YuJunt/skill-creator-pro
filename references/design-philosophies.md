# 技能设计哲学：Capability Primitive vs Process Primitive

> 基于Anthropic官方最佳实践 + effective-agent-skills业界指南整理
> 这是创建技能时第一个要决定的问题——你的技能属于哪种模式？不同模式的设计方法完全不同。

---

## 一、两种设计哲学

### Pattern A: Capability Primitive（能力原语 / 工具包装）

**定义**：技能是确定性CLI或脚本的薄包装，逻辑活在代码里，SKILL.md教agent怎么调用它。

**核心特征**：
- 新增能力（搜索、邮件、浏览器、API访问、文件处理）
- 可靠性来自shell工具，不是prompt
- SKILL.md典型长度：30-80行，主要是命令示例
- agent的工作：理解用户需求→选择正确的命令→执行→解释结果

**什么时候用**：
- 瓶颈是"agent做不了X"（没有这个工具/能力）
- 操作是确定性的、可重复的
- 错误代价高（需要精确执行）
- 已有现成的CLI/API/脚本可以包装

**典型例子**：
- PDF处理技能（包装pdftk/qpdf/pdfplumber）
- 邮件发送技能（包装SMTP/API）
- 数据库查询技能（包装SQL客户端）
- 浏览器自动化技能（包装Playwright）
- 图片处理技能（包装ImageMagick）

---

### Pattern B: Process Primitive（过程原语 / 认知方法论）

**定义**：技能编码agent应该遵循的方法论，纯prompt工程——不需要脚本（或脚本很少）。

**核心特征**：
- 新增结构化工作流（TDD、代码审查、设计对齐、调试循环、研究方法论）
- 可靠性来自明确的流程、checklist、验证循环
- SKILL.md典型长度：100-300行，主要是流程/checklist/示例
- agent的工作：按流程执行→每步检查→验证→迭代

**什么时候用**：
- 瓶颈是"agent的输出质量或流程不好"（有能力但方法不对）
- 任务需要判断/推理/创造力，不能完全脚本化
- 有成熟的方法论/最佳实践可以编码
- 错误代价中等（流程对了质量就有保障）

**典型例子**：
- 代码审查技能（编码审查流程+checklist）
- TDD开发技能（编码红-绿-重构循环）
- 研究综合技能（编码文献检索→主题聚类→交叉验证流程）
- 调试技能（编码复现→定位→修复→验证流程）
- 文档写作技能（编码大纲→草稿→审校→定稿流程）

## 二、两种模式对比

| 维度 | Capability Primitive | Process Primitive |
|------|---------------------|-------------------|
| **解决的问题** | agent做不了X（缺能力） | agent做得不好（缺方法） |
| **逻辑在哪里** | 代码（脚本/CLI/API） | prompt（SKILL.md流程/checklist） |
| **可靠性来源** | shell工具（确定性） | 明确流程+验证循环 |
| **SKILL.md长度** | 30-80行（命令示例为主） | 100-300行（流程/checklist为主） |
| **scripts/目录** | 核心（多个工具脚本） | 可选（少量辅助脚本） |
| **references/目录** | 可选（API文档） | 核心（方法论/规则文档） |
| **agent的角色** | 命令选择者+结果解释者 | 流程执行者+判断决策者 |
| **自由度** | 低（命令是固定的） | 中（流程固定，判断灵活） |
| **测试方法** | 命令执行测试+输出格式验证 | 流程执行测试+输出质量评估 |
| **错误类型** | 命令用错/参数错/环境问题 | 流程跳步/判断错/质量差 |

## 三、如何选择

### 决策树

```
你的技能要解决什么问题？
│
├─ "agent没有这个能力/工具"
│   └─ → Capability Primitive（工具包装）
│
├─ "agent有能力但输出质量/流程不好"
│   └─ → Process Primitive（方法论）
│
└─ "既需要新工具，又需要好方法"
    └─ → 混合模式
```

### 选择检查清单

**选Capability Primitive，如果**：
- [ ] 任务可以用确定性命令/脚本完成
- [ ] 已有现成的CLI/API/库可以包装
- [ ] 错误代价高（需要精确执行）
- [ ] agent的主要工作是选择命令和解释结果
- [ ] 不需要复杂的判断/推理/创造力

**选Process Primitive，如果**：
- [ ] 任务需要判断/推理/创造力
- [ ] 有成熟的方法论/最佳实践可以编码
- [ ] 错误代价中等（流程对了质量就有保障）
- [ ] agent的主要工作是按流程执行和做判断
- [ ] 不能完全脚本化（需要人的/agent的判断）

## 四、混合模式（成熟技能的常态）

**现实中，成熟的技能往往是两种模式的混合**：
- Capability部分给agent更好的工具
- Process部分给agent更好的使用工具的方法

**混合模式的设计原则**：
1. 先确定核心是哪种模式（以一种为主）
2. 另一种模式作为补充，不喧宾夺主
3. Capability部分的脚本要有清晰的输入输出
4. Process部分的流程要明确调用哪些脚本
5. SKILL.md里区分"工具命令"和"工作流程"两个部分

## 五、常见错误

### 错误1：用Process模式解决Capability问题
**症状**：agent需要操作PDF，但技能只写了"PDF处理方法论"，没有实际工具
**修正**：应该用Capability模式，包装现成的PDF处理库

### 错误2：用Capability模式解决Process问题
**症状**：代码审查技能只提供了"运行lint"的命令，没有审查流程/checklist
**修正**：应该用Process模式，编码完整的代码审查流程+checklist

### 错误3：两种模式混杂，没有主次
**症状**：SKILL.md里一半是命令示例，一半是流程，agent不知道先看哪个
**修正**：明确核心模式，另一种作为补充，SKILL.md结构清晰区分

### 错误4：过度脚本化（Capability模式滥用）
**症状**：连需要判断的部分都写成了脚本，agent没有发挥空间
**修正**：确定性部分脚本化，需要判断的部分留给agent（Process模式）

### 错误5：过度prompt化（Process模式滥用）
**症状**：连重复的确定性操作都用prompt描述，让agent每次自己写代码
**修正**：重复的确定性操作脚本化（Capability模式），agent只做判断

## 六、检查清单：你的技能设计哲学是否明确

- [ ] SKILL.md开头或快速开始部分明确说明了设计哲学（Capability/Process/混合）
- [ ] 内容与哲学匹配（Capability以命令示例为主，Process以流程/checklist为主）
- [ ] scripts/目录的角色与哲学匹配（Capability核心，Process可选）
- [ ] references/目录的角色与哲学匹配（Capability可选，Process核心）
- [ ] agent的角色明确（Capability：命令选择者，Process：流程执行者）
- [ ] 没有用错误的模式解决问题（如用Process解决Capability问题）
- [ ] 混合模式有明确的主次，不是两种模式混杂
- [ ] 确定性部分脚本化，需要判断的部分留给agent

**0-3项**：设计哲学不明确，需要重新梳理
**4-6项**：设计哲学基本明确，有优化空间
**7-8项**：设计哲学清晰，技能结构合理

## 多语言设计

> Claude原生支持多语言（中英日法德韩等），技能设计时考虑语言因素：

### description用什么语言？
- **中文用户为主**：description用中文写，触发词包含中英文
- **国际用户**：description用英文写（Claude的系统提示主要是英文）
- **description中可以包含双语触发词**：如"document processing/文档处理"

### SKILL.md正文用什么语言？
- 跟随用户主要语言
- 代码和脚本名保持英文
- 注释和文档说明用用户语言

### 注意事项
- 不要在SKILL.md中混用多种语言写同一段指令（混乱）
- 术语保持一致（要么全用中文术语，要么全用英文术语）
- 触发词覆盖主要用户可能用的语言
