# 技能组合原则（Skill Composition）

> 基于Anthropic官方最佳实践 + effective-agent-skills业界指南整理
> 核心思想：一个技能做一件事（单一职责），复杂任务通过多个技能组合完成。不要做大杂烩技能。

---

## 一、为什么技能组合至关重要

### 1.1 大杂烩技能的问题

**症状**：
- 一个技能既做A又做B还做C，功能越来越多
- SKILL.md越来越长（超过500行），LLM只看前半部分
- 触发不精确（用户说A，技能可能走B的流程）
- 修改一个功能，可能影响其他功能（耦合度高）
- 测试困难（要测试所有功能的组合）
- 复用困难（只想用A功能，不得不加载整个技能）

**根源**：违反单一职责原则，一个技能承担了多个职责。

### 1.2 技能组合的核心价值

1. **聚焦**：每个技能只做一件事，做得深、做得好
2. **灵活**：可以根据任务需要，组合不同的技能
3. **可维护**：修改一个技能，不影响其他技能
4. **可测试**：每个技能可以独立测试
5. **可复用**：一个技能可以被多个任务/组合使用
6. **上下文高效**：只加载需要的技能，不加载无关功能

## 二、单一职责原则

### 2.1 什么是单一职责

**定义**：一个技能只做一件事，只解决一个问题，只服务一个场景。

**判断标准**：
- 技能的name/description能不能用一句话说清楚？
- 技能的功能是不是都围绕同一个核心目标？
- 如果用户说"帮我做X"，是不是明确应该用这个技能？
- 修改这个技能的一个功能，会不会影响其他功能？

### 2.2 单一职责的反面：大杂烩

**反面例子1**：
```
name: all-in-one-tool
description: 帮你做任何事——写代码、写文章、分析数据、处理PDF、发送邮件、管理日程...
```
**问题**：什么都做，什么都做不好；触发不精确；上下文浪费。

**反面例子2**：
```
name: pdf-processor
description: PDF处理——提取文本、合并、拆分、旋转、加密、OCR、翻译、摘要、生成报告...
```
**问题**：PDF处理是核心，但OCR/翻译/摘要/生成报告是不同的职责，应该拆分成多个技能。

### 2.3 如何拆分大杂烩技能

**拆分方法**：
1. 列出技能的所有功能
2. 按职责分组（哪些功能围绕同一个核心目标）
3. 每组成为一个独立的技能
4. 原技能可以作为"入口技能"，负责路由到子技能

**示例**：
```
拆分前：pdf-processor（大杂烩）
  - 提取文本
  - 合并/拆分/旋转
  - 加密/解密
  - OCR
  - 翻译
  - 摘要
  - 生成报告

拆分后：
  - pdf-basic（基础操作：提取文本/合并/拆分/旋转/加密）
  - pdf-ocr（OCR识别）
  - pdf-translate（翻译）
  - pdf-summarize（摘要）
  - pdf-report（生成报告）
  - pdf-hub（入口技能：路由到上面的子技能）
```

## 三、5种技能组合模式

### 模式1：顺序组合（Pipeline）

**定义**：多个技能按顺序执行，前一个的输出是后一个的输入。

**适用场景**：
- 任务有明确的步骤顺序
- 每一步的输出是下一步的输入
- 步骤之间是松耦合的（可以独立替换）

**示例**：
```
数据采集技能 → 数据清洗技能 → 数据分析技能 → 数据可视化技能
     ↓              ↓               ↓               ↓
  原始数据      清洗后数据       分析结果         图表
```

**设计要点**：
- 每个技能的输出格式要标准化（方便下一个技能消费）
- 技能之间通过文件/API/消息传递数据，不是直接调用
- 每个技能可以独立测试（用模拟输入）
- 可以替换某个技能（如换一个更好的数据分析技能）

---

### 模式2：并行组合（Fan-out/Fan-in）

**定义**：多个技能并行执行，最后汇总结果。

**适用场景**：
- 任务可以分解为多个独立的子任务
- 子任务之间没有依赖（可以同时执行）
- 需要汇总多个子任务的结果

**示例**：
```
研究综合任务：
  ├─ 技能A：搜索学术论文
  ├─ 技能B：搜索新闻报道
  ├─ 技能C：搜索行业报告
  └─ 汇总：综合三个来源的信息，生成研究报告
```

**设计要点**：
- 子任务之间没有依赖（可以并行执行）
- 每个子技能的输出格式要标准化（方便汇总）
- 汇总技能负责整合/去重/排序/分析
- 可以增加/减少子技能（如增加一个搜索社交媒体的技能）

---

### 模式3：路由组合（Router + Sub-skills）

**定义**：一个入口技能（Router）根据用户需求，路由到对应的子技能。

**适用场景**：
- 任务有多个模式/场景，每个模式用不同的技能
- 用户需求不明确，需要先判断再选择技能
- 子技能数量多，用户不知道该用哪个

**示例**：
```
pdf-hub（入口技能）：
  用户说"提取PDF文本" → 路由到 pdf-basic
  用户说"OCR识别" → 路由到 pdf-ocr
  用户说"翻译PDF" → 路由到 pdf-translate
  用户说"摘要PDF" → 路由到 pdf-summarize
  用户说"生成报告" → 路由到 pdf-report
```

**设计要点**：
- 入口技能只做路由，不做实际工作
- 路由逻辑要清晰（触发词/模式判断/决策树）
- 子技能是独立的，可以单独使用
- 入口技能的SKILL.md要简洁（只列路由表，不复制子技能的内容）

---

### 模式4：分层组合（Layered Architecture）

**定义**：技能按层次组织，上层依赖下层，下层不依赖上层。

**适用场景**：
- 任务有明确的层次结构（基础层/业务层/应用层）
- 上层功能复用下层能力
- 层次之间是稳定的依赖关系

**示例**：
```
应用层：数据分析报告技能（生成完整的分析报告）
    ↓ 依赖
业务层：数据分析技能（计算指标/识别模式）+ 数据可视化技能（生成图表）
    ↓ 依赖
基础层：数据采集技能（获取数据）+ 数据清洗技能（清洗数据）
```

**设计要点**：
- 层次之间是单向依赖（上层依赖下层，下层不依赖上层）
- 下层是通用的（可以被多个上层复用）
- 上层是专用的（针对具体场景）
- 层次之间的接口要稳定（修改下层不影响上层）

---

### 模式5：主从组合（Master + Worker）

**定义**：一个主技能（Master）协调多个从技能（Worker），主技能做决策，从技能做执行。

**适用场景**：
- 任务复杂，需要协调多个子任务
- 子任务之间有依赖/顺序/条件判断
- 需要动态调整子任务的执行（根据中间结果）

**示例**：
```
主技能：项目管理技能
  - 分析需求 → 决定需要哪些子技能
  - 协调子技能执行（顺序/并行/条件）
  - 汇总结果 → 决定下一步
  - 处理异常 → 重试/回滚/升级

从技能：
  - 需求分析技能
  - 设计技能
  - 编码技能
  - 测试技能
  - 部署技能
```

**设计要点**：
- 主技能只做协调/决策，不做实际工作
- 从技能是独立的，可以单独使用
- 主技能有状态管理（记录子任务的执行情况）
- 主技能有异常处理（子任务失败时怎么办）

## 四、技能组合的设计原则

### 原则1：接口标准化

**做什么**：技能之间的输入输出格式要标准化，方便组合。

**方法**：
- 输入：明确的参数格式（JSON/命令行参数）
- 输出：明确的输出格式（JSON/文件/标准输出）
- 错误：统一的错误格式（错误码/错误信息/错误详情）
- 状态：统一的状态表示（成功/失败/进行中）

**示例**：
```json
{
  "success": true,
  "data": { ... },
  "error": null,
  "metadata": {
    "skill": "data-fetcher",
    "version": "1.0.0",
    "timestamp": "2026-09-22T10:00:00Z"
  }
}
```

---

### 原则2：松耦合

**做什么**：技能之间不要直接依赖，通过标准化接口通信。

**方法**：
- 技能A不直接调用技能B的内部函数
- 技能A通过命令行/API/文件与技能B通信
- 技能A不知道技能B的内部实现（只知道接口）
- 可以替换技能B（只要接口不变）

---

### 原则3：高内聚

**做什么**：每个技能内部的功能要紧密相关，围绕同一个核心目标。

**方法**：
- 技能的所有功能都服务于同一个核心目标
- 不相关的功能拆出去（成为独立技能）
- 技能内部的模块/函数也要高内聚
- 技能的name/description能准确反映其核心目标

---

### 原则4：可独立测试

**做什么**：每个技能可以独立测试，不需要依赖其他技能。

**方法**：
- 技能有明确的输入输出（可以用模拟输入测试）
- 技能不依赖特定的其他技能（只依赖标准化接口）
- 测试用例覆盖正常场景+边界场景+异常场景
- 测试可以自动化（脚本化测试）

---

### 原则5：可独立部署

**做什么**：每个技能可以独立部署/更新，不需要同时更新其他技能。

**方法**：
- 技能是自包含的（SKILL.md + scripts/ + references/）
- 技能不依赖其他技能的内部文件
- 技能的版本号独立管理
- 更新一个技能，不影响其他技能（只要接口不变）

---

## 五、持久化工件（Persistent Artifacts）

### 5.1 什么是持久化工件

**定义**：技能执行过程中产生的、可以被后续技能/任务复用的中间产物。

**为什么重要**：
- 避免重复计算（前一个技能算好的结果，后一个技能直接用）
- 支持断点续跑（任务中断后，可以从持久化工件恢复）
- 支持审计/调试（可以检查中间产物，定位问题）
- 支持异步执行（技能A先执行，把结果存下来，技能B稍后执行）

### 5.2 常见的持久化工件

| 工件类型 | 示例 | 用途 |
|---------|------|------|
| 数据文件 | raw_data.json / cleaned_data.csv | 数据采集/清洗的结果 |
| 分析结果 | analysis_result.json / metrics.json | 数据分析的结果 |
| 图表文件 | chart.png / chart.svg | 数据可视化的结果 |
| 报告文件 | report.md / report.pdf | 报告生成的结果 |
| 状态文件 | state.json / progress.json | 任务执行状态 |
| 日志文件 | run.log / error.log | 执行日志 |

### 5.3 持久化工件的设计原则

1. **标准化格式**：用JSON/CSV/Markdown等标准格式，方便其他技能读取
2. **明确的命名**：文件名包含技能名+时间戳+内容类型（如`data-fetcher_20260922_raw.json`）
3. **元数据**：文件包含元数据（生成时间/生成技能/版本/参数），方便追溯
4. **不可变**：生成后不修改（需要修改时生成新文件，保留历史）
5. **可清理**：有清理机制（临时文件定期清理，重要文件长期保留）

## 六、常见错误

### 错误1：一个技能做所有事（大杂烩）
**症状**：技能功能越来越多，SKILL.md越来越长，触发不精确
**修正**：按单一职责拆分，多个技能组合

### 错误2：技能之间直接调用内部函数
**症状**：技能A直接import技能B的函数，耦合度高，替换困难
**修正**：通过标准化接口（命令行/API/文件）通信，松耦合

### 错误3：没有持久化工件，每次都从头算
**症状**：技能A算好的数据，技能B又重新算一遍，浪费时间
**修正**：用持久化工件（文件/状态）传递中间结果

### 错误4：技能组合没有统一的错误处理
**症状**：一个技能失败了，后续技能继续执行，产生级联错误
**修正**：主技能/编排技能统一处理错误，失败时停止/重试/回滚

### 错误5：技能组合的接口不标准化
**症状**：每个技能的输出格式不一样，组合时需要大量转换代码
**修正**：定义标准化的输入输出格式，所有技能遵守

## 七、检查清单：你的技能组合是否合理

- [ ] 每个技能遵循单一职责（只做一件事）
- [ ] 没有大杂烩技能（功能不超过3-5个相关功能）
- [ ] 技能之间通过标准化接口通信（松耦合）
- [ ] 技能内部功能紧密相关（高内聚）
- [ ] 每个技能可以独立测试（不需要依赖其他技能）
- [ ] 每个技能可以独立部署/更新（不需要同时更新其他技能）
- [ ] 技能组合有明确的模式（顺序/并行/路由/分层/主从）
- [ ] 有持久化工件（中间结果可以复用）
- [ ] 持久化工件有标准化格式+元数据
- [ ] 技能组合有统一的错误处理
- [ ] 技能组合的接口标准化（输入输出格式统一）

**0-4项**：技能组合不合理，需要重新设计
**5-8项**：技能组合基本合理，有优化空间
**9-12项**：技能组合合理，架构清晰
