> 基于业界最佳实践整理的技能评估方法，确保技能质量可量化、可追溯

## 评估维度

### 维度一：触发准确性（Trigger Accuracy）
技能是否在正确的场景下被触发，不在错误的场景下触发。

**评估方法：**
- 准备10-20个测试用例，标记should_trigger或should_not_trigger
- 运行测试，观察技能是否被实际调用
- 计算触发率 = 正确触发数 / 总测试数

**通过标准：**
- should_trigger用例触发率 ≥ 90%
- should_not_trigger用例误触发率 ≤ 10%

**测试用例示例：**
```
should_trigger:
- "帮我分析今天技能"
- "技能决策"
- "今天买什么"

should_not_trigger:
- "帮我分析今天的销售数据"
- "其他领域决策（如股票分析）"
- "其他领域推荐（如旅游推荐）"
```

---

### 维度二：模式选择正确性（Mode Selection Accuracy）
多模式技能是否选择了正确的模式。

**评估方法：**
- 准备每个模式的3-5个测试用例
- 运行测试，观察路由输出的模式是否正确
- 计算模式选择准确率

**通过标准：**
- 模式选择准确率 ≥ 85%

**测试用例示例：**
```
完整分析: "帮我做完整分析"
快速推荐: "快速给我推荐"
规则问答: "功能B怎么用"
结算核对: "帮我核对结果"
效果复盘: "最近效果怎么样"
```

---

### 维度三：输出完整性（Output Completeness）
输出是否包含所有必需字段，格式是否正确。

**评估方法：**
- 定义输出必需字段清单
- 运行3-5次完整流程
- 检查每次输出是否包含所有必需字段
- 计算完整率 = 完整输出数 / 总输出数

**通过标准：**
- 输出完整率 = 100%（不允许遗漏关键字段）

**技能输出必需字段：**
```
- 一句话结论（核心结论+推荐方案+关键指标）
- 主推执行单（方案类型+执行项+数量+关键指标）
- 决策理由（至少3条）
- 风险提示
- 合规声明/免责声明
- 同步状态（如适用）
```

---

### 维度四：流程完整性（Workflow Completeness）
完整工作流是否能跑通，没有断点。

**评估方法：**
- 端到端跑通完整流程（start→continue→settle）
- 检查每个步骤是否成功
- 检查数据是否正确流转

**通过标准：**
- 完整流程跑通率 = 100%
- 每个步骤都有成功输出
- 数据流转正确（start的输出被continue使用，continue的输出被settle使用）

---

### 维度五：边界处理（Edge Case Handling）
异常场景下技能是否能优雅处理，不崩溃。

**评估场景：**
1. 数据不足（<30期）
2. API获取失败
3. 云端写入失败
4. 网络超时
5. 输入格式错误
6. 空输入

**通过标准：**
- 所有边界场景都有明确的错误处理
- 不崩溃（不出现未捕获的异常）
- 有降级机制（如API失败→缓存→报错）
- 错误信息可定位

---

### 维度六：质量门禁有效性（Quality Gate Effectiveness）
校验门禁是否能有效拦截不完整的输出。

**评估方法：**
- 故意构造不完整的输入（缺字段/格式错误）
- 运行continue，观察是否被拦截
- 检查错误信息是否明确

**通过标准：**
- 不完整输入100%被拦截
- 错误信息明确指出缺什么
- 不允许不完整输出通过

---

### 维度七：脚本可靠性（Script Reliability）
脚本是否稳定，没有bug。

**评估方法：**
- 每个脚本运行3次
- 检查是否有报错
- 检查输出是否一致（确定性脚本）

**通过标准：**
- 脚本运行成功率 = 100%
- 确定性脚本输出一致
- 没有未处理的异常

---

### 维度八：多模型一致性（Multi-model Consistency）
不同模型下技能行为是否一致。

**评估方法（环境允许时）：**
- 在2-3个不同模型上运行相同用例
- 比较输出质量和格式
- 计算一致性

**通过标准：**
- 输出格式一致
- 核心结论一致（允许细节差异）
- 不依赖特定模型的特性

**环境限制时：**
- 注明"未做多模型测试，环境限制"
- 提示词设计对模型鲁棒（不依赖特定模型特性）

## 持续评估机制

### 每次更新后
- 运行回归测试（核心用例）
- 检查是否有回归（之前通过的用例现在失败）
- 更新评估报告

### 每周/每月
- 运行完整评估套件
- 统计各维度得分趋势
- 识别逐渐退化的维度

### 生产监控
- 采样生产交互，评估质量
- 设置告警阈值（质量下降到0.85以下告警）
- 维护趋势仪表盘

## 评估工具

### 自动化评估
- 触发评估：关键词匹配 + LLM判断
- 输出完整性：程序化断言（检查字段是否存在）
- 质量门禁：构造异常输入，检查是否被拦截

### 人工评估
- 输出质量：LLM-as-Judge + 人工抽检
- 推理质量：Trajectory Evaluator（检查推理过程是否合理）
- 用户体验：用户反馈收集

### 评估原则
- 能写成代码的就不人工评（稳定、可复现）
- LLM-as-Judge用于质量评估（接近专家判断，但需校准）
- 人工评用于高风险/争议场景（成本高，但不可替代）

# 附录：评估驱动开发（Evaluation-Driven Development）


> 基于Anthropic官方最佳实践 + effective-agent-skills业界指南整理
> 核心思想：先建评估，再写技能。没有评估的技能是不可信的——你不知道它好不好，也不知道改了之后是变好还是变坏。

---

## 一、为什么评估驱动开发至关重要

### 1.1 没有评估的技能是黑箱

**问题**：
- 写了一个技能，觉得"应该能用"，但实际效果如何？不知道
- 改了一个地方，觉得"应该更好了"，但实际是变好还是变坏？不知道
- 用户说"这个技能不好用"，但具体哪里不好用？不知道

**根源**：没有可量化的评估标准，所有判断都是凭感觉。

### 1.2 评估驱动开发的核心价值

1. **可量化**：技能好不好，用数据说话，不是凭感觉
2. **可回归**：改了之后，跑一遍评估，知道是变好还是变坏
3. **可对比**：两个方案哪个好，跑一遍评估就知道
4. **可迭代**：评估发现问题→修复→再评估→持续优化
5. **可交付**：评估报告是技能质量的证明，用户可以信任

---

## 二、评估的四个层次

### Level 1: 触发评估（Trigger Evaluation）

**目标**：技能在正确的时候触发，在错误的时候不触发。

**评估用例**：
```
should_trigger（应该触发）：
  - "帮我创建一个技能" → 应该触发skill-creator
  - "优化一下这个技能" → 应该触发skill-creator
  - "评审技能规范" → 应该触发skill-creator

should_not_trigger（不应该触发）：
  - "帮我写一首诗" → 不应该触发
  - "今天天气怎么样" → 不应该触发
  - "帮我分析股票" → 不应该触发
```

**评估指标**：
- 触发准确率 = 正确触发数 / 总触发数
- 漏触发率 = 应该触发但没触发的数 / 应该触发总数
- 误触发率 = 不应该触发但触发了的数 / 不应该触发总数

**通过标准**：触发准确率≥95%，漏触发率≤5%，误触发率≤5%

---

### Level 2: 模式评估（Mode Evaluation）

**目标**：不同模式下，技能走正确的流程，输出正确的格式。

**评估用例**：
```
以skill-creator为例：
  - "创建技能" → 应该走新建模式，输出技能创建完成报告
  - "优化技能" → 应该走优化模式，输出优化方案+实施结果
  - "评审技能" → 应该走评审模式，输出评审报告
  - "测试技能" → 应该走测试模式，输出测试报告

边界用例：
  - "创建技能，然后评审一下" → 应该先创建，再评审
  - "快速创建一个技能" → 应该走简化流程，不是完整流程
```

**评估指标**：
- 模式识别准确率 = 正确识别模式数 / 总用例数
- 流程执行正确率 = 正确执行流程数 / 总用例数
- 输出格式正确率 = 输出格式正确数 / 总用例数

**通过标准**：模式识别准确率≥90%，流程执行正确率≥90%

---

### Level 3: 边界评估（Boundary Evaluation）

**目标**：异常输入、数据不足、网络失败等边界场景下，技能行为正确（不崩溃、有降级、有错误提示）。

**评估用例**：
```
异常输入：
  - 技能名称包含特殊字符 → 应该报错提示格式错误
  - 路径不存在 → 应该报错提示路径不存在
  - 空输入 → 应该提示需要输入

数据不足：
  - 审计一个空目录 → 应该提示缺少SKILL.md
  - 校验一个只有SKILL.md的技能 → 应该正常运行，报告缺少scripts/references

网络失败：
  - API调用失败 → 应该有降级机制（缓存/报错）
  - 云端写入失败 → 应该本地备份，提示稍后重试

环境问题：
  - 缺少依赖 → 应该提示需要安装什么
  - 权限不足 → 应该提示权限问题
```

**评估指标**：
- 崩溃率 = 崩溃用例数 / 总用例数（目标：0%）
- 降级正确率 = 正确降级数 / 需要降级数
- 错误提示清晰度 = 错误提示可理解数 / 总错误数

**通过标准**：崩溃率=0%，降级正确率≥90%

---

### Level 4: 质量评估（Quality Evaluation）

**目标**：技能的输出质量是否达标（内容正确、结构完整、符合规范）。

**评估用例**：
```
以skill-creator创建的技能为例：
  - 创建的技能是否符合36项检查清单？
  - 创建的SKILL.md是否有正确的frontmatter？
  - 创建的脚本是否能正常运行？
  - 创建的references是否有内容（不是空模板）？

以优化技能为例：
  - 优化后的技能36项得分是否提升？
  - 优化是否引入了新的问题？
  - 优化是否保持了原有功能？

以评审技能为例：
  - 评审报告是否覆盖了所有36项？
  - 问题分级是否合理？
  - 改进建议是否具体可执行？
```

**评估指标**：
- 内容正确率 = 内容正确数 / 总检查项
- 结构完整率 = 结构完整数 / 总检查项
- 规范符合率 = 符合规范数 / 总检查项
- 用户满意度 = 满意用户数 / 总用户数（主观评估）

**通过标准**：内容正确率≥90%，规范符合率≥90%

## 三、评估驱动开发流程

### Step 1: 定义评估用例（写技能之前）

**做什么**：在写技能之前，先定义评估用例——什么输入应该产生什么输出。

**模板**：
```markdown
## 评估用例：{技能名}

### 触发评估
| 输入 | 预期 | 实际 | 通过？ |
|------|------|------|--------|
| ... | ... | ... | ... |

### 模式评估
| 输入 | 预期模式 | 预期输出 | 实际 | 通过？ |
|------|---------|---------|------|--------|
| ... | ... | ... | ... | ... |

### 边界评估
| 场景 | 输入 | 预期行为 | 实际 | 通过？ |
|------|------|---------|------|--------|
| ... | ... | ... | ... | ... |

### 质量评估
| 检查项 | 预期 | 实际 | 通过？ |
|--------|------|------|--------|
| ... | ... | ... | ... |
```

**原则**：
- 评估用例要具体，不是抽象的"应该好用"
- 覆盖正常场景+边界场景+异常场景
- 每个用例有明确的通过/不通过标准
- 至少3个触发用例+3个模式用例+3个边界用例

---

### Step 2: 写技能（实现功能）

**做什么**：按照评估用例的要求，实现技能功能。

**原则**：
- 每个功能都有对应的评估用例
- 不写没有评估用例的功能（避免过度设计）
- 写的过程中随时跑评估，确保不偏离目标

---

### Step 3: 跑评估（验证功能）

**做什么**：运行所有评估用例，记录结果。

**方法**：
- 自动化评估：能脚本化的评估用脚本跑（如规范校验、深度审计）
- 人工评估：需要判断质量的用例人工跑（如输出质量、用户体验）
- A/B对比：两个方案哪个好，用相同的评估用例对比

**输出**：
```
评估报告：{技能名}
日期：{日期}
版本：{版本}

总体通过率：{X}/{Y} ({Z}%)

各层通过率：
- 触发评估：{X}/{Y}
- 模式评估：{X}/{Y}
- 边界评估：{X}/{Y}
- 质量评估：{X}/{Y}

未通过用例：
1. {用例描述} → {实际结果} → {修复计划}
2. ...
```

---

### Step 4: 修复问题（迭代优化）

**做什么**：根据评估报告，修复未通过的用例。

**原则**：
- 高优先级问题（触发错误/崩溃）必须立即修复
- 中优先级问题（模式错误/质量差）建议修复
- 低优先级问题（边界场景/体验优化）可选修复
- 修复后重新跑评估，确保修复有效且没有引入新问题

---

### Step 5: 持续评估（每次修改后）

**做什么**：每次修改技能后，都跑一遍评估，确保没有回归。

**原则**：
- 修改前跑一遍（基线）
- 修改后跑一遍（对比）
- 如果通过率下降，说明修改引入了问题，需要回滚或修复
- 评估用例持续更新（发现新问题就加新用例）

---

## 四、评估工具与方法

### 4.1 自动化评估工具

| 工具 | 用途 | 适用层次 |
|------|------|---------|
| validate_skill.py | 规范校验（frontmatter/目录结构/引用） | 触发+边界 |
| audit_skill.py | 深度审计（36项检查+评分） | 质量 |
| 脚本执行测试 | 运行脚本，检查是否崩溃/输出是否正确 | 边界+质量 |
| 输出格式验证 | 检查输出是否符合模板格式 | 模式+质量 |

### 4.2 人工评估方法

| 方法 | 用途 | 适用层次 |
|------|------|---------|
| 触发测试 | 输入各种用户消息，看技能是否正确触发 | 触发 |
| 模式测试 | 输入不同模式的请求，看是否走正确流程 | 模式 |
| 边界测试 | 输入异常/边界数据，看行为是否正确 | 边界 |
| 质量评估 | 人工判断输出质量是否达标 | 质量 |
| 用户测试 | 让真实用户使用，收集反馈 | 质量 |

### 4.3 A/B对比测试

**方法**：两个方案（A和B）用相同的评估用例测试，对比结果。

**适用场景**：
- 两个设计方案哪个好
- 修改前后哪个好
- 两个技能哪个好

**输出**：
```
A/B对比报告：{方案A} vs {方案B}
评估用例数：{N}

方案A通过率：{X}%
方案B通过率：{Y}%

方案A优势用例：{列出}
方案B优势用例：{列出}
持平用例：{列出}

结论：{方案A/B更好，或各有优势}
```

## 五、常见错误

### 错误1：先写技能，后补评估
**症状**：技能写完了，才想起来要评估，评估用例是根据现有输出写的（不是根据预期输出写的）
**修正**：评估驱动开发——先写评估用例，再写技能

### 错误2：评估用例太少
**症状**：只有2-3个用例，覆盖不了各种场景，评估结果不可信
**修正**：至少3个触发+3个模式+3个边界+3个质量，共12个用例

### 错误3：只评估正常场景，不评估边界场景
**症状**：正常输入没问题，但异常输入就崩溃
**修正**：边界评估是必须的，覆盖异常输入/数据不足/网络失败/环境问题

### 错误4：评估一次就完事，不持续评估
**症状**：第一次评估通过了，之后修改不再评估，引入了回归问题
**修正**：每次修改后都跑评估，确保没有回归

### 错误5：评估用例不更新
**症状**：评估用例还是最初的，新发现的问题没有加进去
**修正**：发现新问题就加新用例，评估用例持续更新

## 六、检查清单：你的技能是否有完整的评估

- [ ] 写技能之前先定义了评估用例
- [ ] 评估用例覆盖4个层次（触发/模式/边界/质量）
- [ ] 每个层次至少3个用例
- [ ] 评估用例有明确的通过/不通过标准
- [ ] 有自动化评估工具（规范校验/深度审计/脚本测试）
- [ ] 有人工评估方法（触发测试/模式测试/质量评估）
- [ ] 每次修改后都跑评估，确保没有回归
- [ ] 评估用例持续更新（发现新问题就加新用例）
- [ ] 有评估报告（记录每次评估的结果）
- [ ] 未通过用例有修复计划和跟踪

**0-4项**：评估严重不足，技能质量不可信
**5-7项**：评估基本完整，有优化空间
**8-11项**：评估完整，技能质量可信

## 基准回归模式（Benchmark Regression）

> 模型更新后重新跑eval，确保技能没有因模型变化而退化。

### 什么时候跑基准回归

| 触发时机 | 说明 |
|---------|------|
| 模型版本更新后 | Claude模型升级，行为可能变化 |
| 重大技能修改后 | 改了核心逻辑，确认没有退化 |
| 每季度定期 | 防止渐进式退化 |

### 回归对比指标

| 指标 | 说明 |
|------|------|
| eval通过率 | 与基准对比，下降>5%需要调查 |
| 平均耗时 | 与基准对比，增加>20%需要调查 |
| token用量 | 与基准对比，增加>20%需要调查 |
| 触发率 | 与基准对比，下降>10%需要调查 |

### 流程

```
1. 保存当前eval结果作为基准（baseline）
2. 模型更新/技能修改后，重跑同样的eval
3. 对比新旧结果
4. 退化项：调查原因，修复或接受
5. 进步项：记录经验
```
