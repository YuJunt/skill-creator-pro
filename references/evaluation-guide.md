# 技能评估与测试指南

> 基于业界最佳实践整理的技能评估方法，确保技能质量可量化、可追溯

---

## 评估维度

### 维度一：触发准确性（Trigger Accuracy）
技能是否在正确的场景下被触发，不在错误的场景下触发。

**评估方法：**
- 准备10-20个测试用例，标记should_trigger或should_not_trigger
- 运行测试，观察技能是否被实际调用
- 计算触发率 = 正确触发数 / 总测试数

**通过标准：**
- should_trigger用例触发率 ≥ 90%
- should_not_trigger用例误触发率 ≤ 10%

**测试用例示例：**
```
should_trigger:
- "帮我分析今天技能"
- "技能决策"
- "今天买什么"

should_not_trigger:
- "帮我分析今天的销售数据"
- "其他领域决策（如股票分析）"
- "其他领域推荐（如旅游推荐）"
```

---

### 维度二：模式选择正确性（Mode Selection Accuracy）
多模式技能是否选择了正确的模式。

**评估方法：**
- 准备每个模式的3-5个测试用例
- 运行测试，观察路由输出的模式是否正确
- 计算模式选择准确率

**通过标准：**
- 模式选择准确率 ≥ 85%

**测试用例示例：**
```
完整分析: "帮我做完整分析"
快速推荐: "快速给我推荐"
规则问答: "功能B怎么用"
结算核对: "帮我核对结果"
效果复盘: "最近效果怎么样"
```

---

### 维度三：输出完整性（Output Completeness）
输出是否包含所有必需字段，格式是否正确。

**评估方法：**
- 定义输出必需字段清单
- 运行3-5次完整流程
- 检查每次输出是否包含所有必需字段
- 计算完整率 = 完整输出数 / 总输出数

**通过标准：**
- 输出完整率 = 100%（不允许遗漏关键字段）

**技能输出必需字段：**
```
- 一句话结论（核心结论+推荐方案+关键指标）
- 主推执行单（方案类型+执行项+数量+关键指标）
- 决策理由（至少3条）
- 风险提示
- 合规声明/免责声明
- 同步状态（如适用）
```

---

### 维度四：流程完整性（Workflow Completeness）
完整工作流是否能跑通，没有断点。

**评估方法：**
- 端到端跑通完整流程（start→continue→settle）
- 检查每个步骤是否成功
- 检查数据是否正确流转

**通过标准：**
- 完整流程跑通率 = 100%
- 每个步骤都有成功输出
- 数据流转正确（start的输出被continue使用，continue的输出被settle使用）

---

### 维度五：边界处理（Edge Case Handling）
异常场景下技能是否能优雅处理，不崩溃。

**评估场景：**
1. 数据不足（<30期）
2. API获取失败
3. 云端写入失败
4. 网络超时
5. 输入格式错误
6. 空输入

**通过标准：**
- 所有边界场景都有明确的错误处理
- 不崩溃（不出现未捕获的异常）
- 有降级机制（如API失败→缓存→报错）
- 错误信息可定位

---

### 维度六：质量门禁有效性（Quality Gate Effectiveness）
校验门禁是否能有效拦截不完整的输出。

**评估方法：**
- 故意构造不完整的输入（缺字段/格式错误）
- 运行continue，观察是否被拦截
- 检查错误信息是否明确

**通过标准：**
- 不完整输入100%被拦截
- 错误信息明确指出缺什么
- 不允许不完整输出通过

---

### 维度七：脚本可靠性（Script Reliability）
脚本是否稳定，没有bug。

**评估方法：**
- 每个脚本运行3次
- 检查是否有报错
- 检查输出是否一致（确定性脚本）

**通过标准：**
- 脚本运行成功率 = 100%
- 确定性脚本输出一致
- 没有未处理的异常

---

### 维度八：多模型一致性（Multi-model Consistency）
不同模型下技能行为是否一致。

**评估方法（环境允许时）：**
- 在2-3个不同模型上运行相同用例
- 比较输出质量和格式
- 计算一致性

**通过标准：**
- 输出格式一致
- 核心结论一致（允许细节差异）
- 不依赖特定模型的特性

**环境限制时：**
- 注明"未做多模型测试，环境限制"
- 提示词设计对模型鲁棒（不依赖特定模型特性）

## 评估用例模板

### 触发评估用例
```json
{
  "name": "trigger-eval-001",
  "type": "should_trigger",
  "input": "帮我分析今天技能",
  "expected": "my-skill skill triggered"
}
```

### 模式选择评估用例
```json
{
  "name": "mode-eval-001",
  "type": "mode_selection",
  "input": "快速给我推荐",
  "expected_mode": "快速推荐",
  "expected_pipeline": "start(quick)→简短分析→continue"
}
```

### 边界评估用例
```json
{
  "name": "edge-eval-001",
  "type": "edge_case",
  "scenario": "数据不足",
  "setup": "模拟只有10期历史数据",
  "expected": "输出'数据不足，结论仅供参考'，不崩溃"
}
```

### 质量门禁评估用例
```json
{
  "name": "gate-eval-001",
  "type": "quality_gate",
  "scenario": "缺路由模式字段",
  "input": {"report": {"摘要": "测试", "推荐结果": "123"}},
  "expected": "continue报错：'Step0: 缺路由模式'"
}
```

## 持续评估机制

### 每次更新后
- 运行回归测试（核心用例）
- 检查是否有回归（之前通过的用例现在失败）
- 更新评估报告

### 每周/每月
- 运行完整评估套件
- 统计各维度得分趋势
- 识别逐渐退化的维度

### 生产监控
- 采样生产交互，评估质量
- 设置告警阈值（质量下降到0.85以下告警）
- 维护趋势仪表盘

## 评估工具

### 自动化评估
- 触发评估：关键词匹配 + LLM判断
- 输出完整性：程序化断言（检查字段是否存在）
- 质量门禁：构造异常输入，检查是否被拦截

### 人工评估
- 输出质量：LLM-as-Judge + 人工抽检
- 推理质量：Trajectory Evaluator（检查推理过程是否合理）
- 用户体验：用户反馈收集

### 评估原则
- 能写成代码的就不人工评（稳定、可复现）
- LLM-as-Judge用于质量评估（接近专家判断，但需校准）
- 人工评用于高风险/争议场景（成本高，但不可替代）
