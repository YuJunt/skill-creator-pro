# 端到端实测完整流程模板

> 基于技能实战多轮开发实战总结。端到端实测不是"跑一下脚本看看有没有报错"，而是覆盖全流程、全场景、全维度的系统性测试。
> 核心结论：**没有端到端实测的技能是不可靠的——单元测试通过不代表全流程能跑通，全流程能跑通不代表所有场景都正确。实战中，多轮修改后从未完整跑通create→optimize→review→test全流程，直到做了7维度深度实测才发现多个bug。**

---

## 一、什么是端到端实测

### 1.1 定义

端到端实测（End-to-End Testing）是指从用户触发技能开始，到最终输出结果并持久化的完整流程测试，覆盖所有环节、所有场景、所有边界条件。

### 1.2 端到端实测 vs 单元测试 vs 集成测试

| 测试类型 | 范围 | 目的 | 技能案例 |
|---------|------|------|-----------|
| 单元测试 | 单个函数/脚本 | 验证函数逻辑正确 | validate_skill.py的规范校验函数 |
| 集成测试 | 多个脚本协作 | 验证脚本间接口正确 | init_skill_pro.py→validate_skill.py→audit_skill.py |
| 端到端实测 | 完整用户流程 | 验证从触发到输出的全流程 | 用户说"创建技能"→create_skill.py start→创建→output_validator→交付 |

### 1.3 为什么端到端实测至关重要

实战发现的问题：
```
问题1：单元测试全通过，但完整流程跑不通
  根因：create_skill.py continue校验路由模式字段，但start没有输出这个字段
  单元测试测不到这个问题，因为只测了单个脚本

问题2：正常场景能跑通，但异常场景崩溃
  根因：非UTF-8编码文件导致validate_skill.py崩溃
  正常测试用例都是UTF-8，测不到这个问题

问题3：脚本单独运行正常，但编排脚本调用失败
  根因：create_skill.py用subprocess调用脚本，但工作目录不对
  单独运行脚本时工作目录正确，测不到这个问题

问题4：云端写入成功，但字段映射错误
  根因：continue阶段把"信号强度"写成了字符串，但云端表是number类型
  本地测试不连云端，测不到这个问题
```

## 二、端到端实测的7个维度

### 维度1：正常场景测试

**目的**：验证技能在正常使用场景下能完整跑通。

**测试用例**：
```
用例1.1：新建技能模式（create）
  - 触发：用户说"帮我创建一个新技能"
  - 预期：需求分析→架构设计→模板生成→内容编写→校验→测试，输出完整技能
  - 验证点：
    - create_skill.py create按顺序执行所有步骤
    - init_skill_pro.py生成正确的目录结构
    - validate_skill.py规范校验通过
    - audit_skill.py深度审计必备层全部达标
    - 输出格式符合新建技能交付模板

用例1.2：优化技能模式（optimize）
  - 触发：用户说"优化一下这个技能"
  - 预期：现状审计→问题定位→方案设计→实施→回归测试
  - 验证点：
    - create_skill.py optimize先运行audit_skill.py检查现状
    - 优化后规范校验和深度审计都通过
    - 未引入新问题
    - 输出格式符合优化技能交付模板

用例1.3：深度评审模式（review）
  - 触发：用户说"评审一下这个技能"
  - 预期：36项逐项核查→问题分级→改进建议→优先级排序
  - 验证点：
    - create_skill.py review运行规范校验+深度审计
    - 输出完整评审报告（三层得分+高/中/低优先级问题）
    - 问题分级正确
    - 改进建议具体可执行

用例1.4：端到端测试模式（test）
  - 触发：用户说"测试一下这个技能"
  - 预期：触发测试→模式测试→边界测试→回归测试→报告
  - 验证点：
    - create_skill.py test运行规范校验+深度审计+输出格式校验
    - output_validator.py 0个必须修复问题
    - 输出完整测试报告
    - 所有测试步骤都通过
```

### 维度2：边界场景测试

**目的**：验证技能在边界条件下的行为。

**测试用例**：
```
用例2.1：用户需求不明确
  - 构造：用户只说"创建一个技能"，不说明技能目标和触发场景
  - 预期：主动询问用户需求，不盲目创建
  - 验证点：
    - 输出澄清问题（至少3个关键问题）
    - 不直接生成技能
    - 不崩溃

用例2.2：技能名称不合法
  - 构造：用户指定技能名称为"My Skill!"（含空格和特殊字符）
  - 预期：校验名称格式，提示用户修改
  - 验证点：
    - init_skill_pro.py校验名称格式
    - 输出错误信息和修正建议
    - 不创建不合法的技能目录

用例2.3：输出目录不存在
  - 构造：用户指定--path为不存在的目录
  - 预期：自动创建目录或提示用户指定有效目录
  - 验证点：
    - init_skill_pro.py处理目录不存在的情况
    - 输出提示信息
    - 不崩溃

用例2.4：校验发现高优先级问题
  - 构造：创建出的技能SKILL.md缺少frontmatter
  - 预期：validate_skill.py报错，不允许继续交付
  - 验证点：
    - validate_skill.py检测到高优先级问题
    - 输出具体错误信息和修复建议
    - 不允许跳过校验直接交付

用例2.5：设计哲学选择不当
  - 构造：用户要创建简单工具包装型技能，但选择了mixed模式
  - 预期：建议用户选择更合适的设计哲学
  - 验证点：
    - 分析技能需求与设计哲学的匹配度
    - 输出设计哲学选择建议
    - 不盲目按用户选择生成

用例2.6：references文档未被引用
  - 构造：创建的技能有references文档但SKILL.md中未引用
  - 预期：output_validator.py检测到未引用的文档，提示补充引用
  - 验证点：
    - output_validator.py检测到未引用的references文档
    - 输出具体未引用的文档列表
    - 建议在SKILL.md中添加引用
```

### 维度3：异常场景测试

**目的**：验证技能在异常输入/异常环境下的鲁棒性。

**测试用例**：
```
用例3.1：非UTF-8编码文件
  - 构造：SKILL.md用GBK编码保存
  - 预期：优雅处理，不崩溃
  - 验证点：
    - validate_skill.py不崩溃
    - audit_skill.py不崩溃
    - 输出错误提示

用例3.2：空目录
  - 构造：技能目录为空（没有SKILL.md）
  - 预期：明确报错"缺少SKILL.md"
  - 验证点：
    - 不崩溃
    - 错误信息准确
    - summary正确统计

用例3.3：路径不存在
  - 构造：校验一个不存在的路径
  - 预期：明确报错"路径不存在"
  - 验证点：
    - 不崩溃
    - 错误信息准确（不是"缺少SKILL.md"）
    - summary正确统计

用例3.4：超大文件
  - 构造：SKILL.md有10000行（384K）
  - 预期：正常处理，性能可接受
  - 验证点：
    - validate_skill.py在100ms内完成
    - audit_skill.py在200ms内完成
    - 不崩溃

用例3.5：云端写入失败
  - 构造：云端数据库 token错误或网络断开
  - 预期：本地备份，提示稍后手动同步
  - 验证点：
    - 不崩溃
    - 本地备份文件生成
    - 输出提示信息
```

### 维度4：脚本全场景测试

**目的**：验证每个脚本在各种输入下的行为。

**测试用例**：
```
用例4.1：validate_skill.py全场景
  - 正常技能：通过
  - 缺SKILL.md：高优先级报错
  - 路径不存在：高优先级报错
  - 非UTF-8编码：优雅处理
  - 超大文件：性能可接受
  - 缺frontmatter：报错
  - description缺触发词：中优先级警告
  - SKILL.md超500行：中优先级警告
  - references未引用：低优先级警告
  - 脚本缺main入口：低优先级警告

用例4.2：audit_skill.py全场景
  - 正常技能：输出36项评分
  - 缺SKILL.md：报错
  - 路径不存在：报错（信息准确）
  - 非UTF-8编码：优雅处理
  - 空目录：报错
  - 重复运行：结果一致
  - 各层评分正确：规范层/架构层/内容层/工程层/质量层/进化层/运维层

用例4.3：init_skill_pro.py全场景
  - 正常创建：生成完整目录结构
  - 非法技能名：拦截
  - 目录已存在：拦截
  - 生成后校验：通过validate_skill.py
  - 生成后审计：有基础分
  - 脚本模板可运行：main/orchestrator/validator不崩溃
```

### 维度5：端到端闭环测试

**目的**：验证从创建到优化的完整闭环。

**测试用例**：
```
用例5.1：创建→校验→审计→优化→回归
  步骤：
    1. init_skill_pro.py创建新技能
    2. validate_skill.py校验（预期：基础通过）
    3. audit_skill.py审计（预期：基线分~23分）
    4. 模拟优化：添加触发路由/Gotchas/编排脚本/校验门禁
    5. 再次audit（预期：分数提升到~34分）
    6. 再次validate（预期：仍然通过）
  验证点：
    - 审计能发现问题（基线分低）
    - 优化后分数提升（+11分）
    - 优化后仍然通过校验
    - 分数提升可解释（哪些项从fail变pass）

用例5.2：故意引入问题→校验能发现
  步骤：
    1. 取一个正常技能
    2. 故意删除frontmatter的description
    3. validate_skill.py校验（预期：发现高优先级问题）
    4. 故意让SKILL.md超过500行
    5. validate_skill.py校验（预期：发现中优先级问题）
  验证点：
    - 校验能发现故意引入的问题
    - 问题级别正确（高/中/低）
    - 错误信息准确
```

### 维度6：真实技能交叉审计

**目的**：用audit_skill.py审计真实存在的技能，验证审计脚本的实用性。

**测试用例**：
```
用例6.1：审计技能实战
  - 预期：~32分（良好），有具体的改进建议
  - 验证点：
    - 各层评分合理
    - 问题列表具体可操作
    - 能发现技能的真实问题（如运维层不足）

用例6.2：审计数据分析技能
  - 预期：~26分（合格）
  - 验证点：
    - 能发现技能的问题
    - 与技能的评分有差异（不同技能问题不同）

用例6.3：审计skill-creator-pro自身
  - 预期：~33分（优秀）
  - 验证点：
    - 自审不崩溃
    - 分数合理
    - 能发现自身的不足
```

### 维度7：压力与性能测试

**目的**：验证技能在高负载/大数据量下的性能和稳定性。

**测试用例**：
```
用例7.1：超大文件性能
  - 构造：10000行SKILL.md（384K）
  - 预期：validate<100ms, audit<200ms

用例7.2：多脚本目录性能
  - 构造：30个Python脚本的目录
  - 预期：audit<100ms

用例7.3：重复运行一致性
  - 构造：同一技能运行10次
  - 预期：10次结果完全一致

用例7.4：并发运行
  - 构造：同时运行3个audit
  - 预期：全部成功，结果一致

用例7.5：空文件处理
  - 构造：0字节的SKILL.md
  - 预期：优雅处理，不崩溃

用例7.6：非UTF-8编码
  - 构造：GBK编码的SKILL.md
  - 预期：优雅处理，不崩溃

用例7.7：深层嵌套目录
  - 构造：scripts/sub/sub/sub/目录
  - 预期：正常处理

用例7.8：特殊字符文件名
  - 构造：文件名含中文/空格/特殊字符
  - 预期：正常处理
```

## 三、端到端实测的执行流程

### 3.1 测试前准备

```
1. 确认测试环境：Python版本、依赖库、云端连接
2. 准备测试数据：正常数据/边界数据/异常数据
3. 准备测试工作区：/tmp/skill-test-XXXX/
4. 备份原始技能：测试不影响生产环境
5. 确认测试用例清单：7个维度的所有用例
```

### 3.2 测试执行

```
按维度顺序执行：
  维度1（正常场景）→ 维度2（边界场景）→ 维度3（异常场景）
  → 维度4（脚本全场景）→ 维度5（端到端闭环）→ 维度6（交叉审计）
  → 维度7（压力性能）

每个用例：
  1. 构造测试环境/数据
  2. 执行测试命令
  3. 记录实际结果
  4. 与预期结果对比
  5. 标记通过/失败
  6. 失败时记录bug详情
```

### 3.3 Bug修复与回归

```
发现bug后：
  1. 记录bug（级别/位置/描述/复现步骤）
  2. 按级别排序修复（P0立即/P1 24h/P2本周/P3下次）
  3. 修复后回归测试：
     - 修复的用例通过
     - 之前通过的用例仍然通过（无回归）
     - 性能不下降
  4. 所有bug修复后，重新运行全部测试用例
```

### 3.4 测试报告

```
测试报告必须包含：
  1. 测试概述：时间/环境/测试范围
  2. 7个维度的通过情况：通过数/总数/通过率
  3. Bug列表：级别/位置/描述/状态
  4. 性能数据：关键操作的耗时
  5. 结论：是否可以投入生产使用
  6. 待改进项：后续优化建议
```

## 四、实战的端到端实测经验

### v1.0：只跑单元测试（问题最多）
```
- 每个脚本单独跑一下，不报错就算通过
- 从未完整跑通create→optimize→review→test全流程
- 结果：上线后optimize报错，因为参数格式不匹配
```

### v2.0：跑正常场景（改善有限）
```
- 完整跑通了正常模式的start→continue
- 但没测异常场景和边界场景
- 结果：非UTF-8编码文件导致脚本崩溃，用户第一次用就报错
```

### v3.0：7维度深度实测（有效）
```
- 覆盖7个维度，50+测试用例
- 发现7个bug（2个严重/1个高/2个中/2个低）
- 全部修复后回归验证通过
- 结果：技能稳定性大幅提升，可投入生产使用
```

## 五、检查清单：你的技能是否做了完整的端到端实测

- [ ] 是否有正常场景测试（所有模式都测过）？
- [ ] 是否有边界场景测试（数据不足/API失败/预算超支等）？
- [ ] 是否有异常场景测试（非UTF-8/空目录/路径不存在等）？
- [ ] 是否有脚本全场景测试（每个脚本的各种输入）？
- [ ] 是否有端到端闭环测试（创建→校验→审计→优化→回归）？
- [ ] 是否有真实技能交叉审计（审计其他真实技能）？
- [ ] 是否有压力与性能测试（大文件/多脚本/并发/重复运行）？
- [ ] 发现的bug是否全部修复并回归验证？
- [ ] 是否有测试报告（通过情况/bug列表/性能数据/结论）？
- [ ] 每次修改后是否回归测试？

**0-4项**：端到端实测严重不足，技能不可靠
**5-7项**：端到端实测基本完整，但可能有遗漏
**8-11项**：端到端实测完整，技能可靠
