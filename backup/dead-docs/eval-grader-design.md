# 评估分级器设计指南（Eval Grader Design）

> 基于Anthropic官方Evals框架（three types of graders: code-based / model-based / human）。
> 核心结论：**code-based grader管"对不对"，model-based grader管"好不好"，human管"信不信"。三种grader组合使用，缺一不可。**

---

## 一、为什么需要三种grader

### 1.1 单种grader的局限

| Grader类型 | 擅长 | 不擅长 | 单独使用的问题 |
|-----------|------|--------|---------------|
| **code-based** | 字符串匹配/二进制测试/静态分析/结果验证/工具调用验证 | 主观质量/格式美感/逻辑深度 | 太严格，合法变体不通过 |
| **model-based** | 开放式输出质量/逻辑连贯性/格式美感/多维度评分 | 精确数值/精确格式 | 不稳定，需要多次采样 |
| **human** | 业务正确性/用户满意度/长期价值 | 大规模/快速/便宜 | 慢/贵/不可复现 |

### 1.2 组合使用原则

```
┌─────────────────────────────────────────┐
│  输出质量金字塔                          │
│                                         │
│  🔺 第3层：human judge（10%）           │
│     抽检关键样本，校准model-based       │
│                                         │
│  🔷 第2层：model-based judge（30%）     │
│     LLM-as-judge评分开放式输出质量      │
│                                         │
│  ⬜ 第1层：code-based judge（60%）     │
│     自动化校验结构/格式/关键字段       │
│                                         │
│  ──────────────────────────────────    │
│  技能输出                               │
└─────────────────────────────────────────┘
```

**比例建议**：60%自动化（code-based）+ 30% LLM评分（model-based）+ 10%人工抽检（human）

## 二、Code-based Grader（自动化校验）

### 2.1 适合code-based的检查项

| 检查类型 | 例子 | 实现方式 |
|---------|------|---------|
| **字符串匹配** | 输出必须包含"✅ 校验通过" | `assert "✅" in output` |
| **二进制测试** | 校验通过/失败退出码 | `assert returncode == 0` |
| **静态分析** | SKILL.md行数<500/frontmatter字段完整 | `validate_skill.py` |
| **结果验证** | 计算正确/结果核对正确 | `check.py` |
| **工具调用验证** | 是否调用了正确的脚本/参数 | 解析Bash命令 |
| **格式校验** | JSON Schema/YAML frontmatter | `jsonschema.validate()` |

### 2.2 code-based grader的局限

- ❌ 不适合判断"分析是否深入"
- ❌ 不适合判断"建议是否合理"
- ❌ 不适合判断"格式是否美观"
- ❌ 对合法变体太严格（"✅通过" vs "✅ 通过"）

---

## 三、Model-based Grader（LLM-as-Judge）

### 3.1 什么时候用model-based grader

| 场景 | 例子 |
|------|------|
| 开放式输出质量 | 分析报告是否有深度/建议是否合理 |
| 逻辑连贯性 | 推理过程是否自洽/有没有矛盾 |
| 格式美感 | 输出是否易读/结构是否清晰 |
| 多维度评分 | 同时评估多个维度（深度/准确度/可读性） |
| 风格匹配 | 输出是否符合预期风格（专业/简洁/口语化） |

### 3.2 Model-based grader设计模板

```markdown
## 评分任务

你是一个严格的技能输出质量评审专家。请按以下维度评分（1-5分）：

### 评分维度

| 维度 | 5分（优秀） | 3分（合格） | 1分（不合格） |
|------|------------|------------|--------------|
| **完整性** | 包含所有必需字段，无遗漏 | 缺少1个次要字段 | 缺少关键字段 |
| **准确性** | 所有数据/计算正确 | 1个小错误不影响结论 | 关键错误 |
| **深度** | 分析深入，有独立判断 | 表面分析，套用模板 | 无分析，只列数据 |
| **格式** | 结构清晰，易读 | 基本可读 | 混乱难读 |

### 评分要求
1. 每个维度独立评分，不要因为一个维度好就全部打高分
2. 必须引用具体证据（哪句话/哪个字段），不能凭感觉
3. 如果不确定，打中间分（3分），不要走极端
4. 总分 = 4个维度平均分

### 输出格式
```json
{
  "completeness": 5,
  "accuracy": 4,
  "depth": 3,
  "format": 4,
  "overall": 4.0,
  "evidence": "完整性：包含全部6个字段；深度：分析较浅，没有独立判断",
  "suggestions": "建议增加独立概率估计和矛盾信号分析"
}
```
```

### 3.3 Model-based grader的注意事项

| 注意事项 | 说明 |
|---------|------|
| **多次采样** | 同一任务跑3次，取平均分，减少随机性 |
| **明确评分标准** | 每个分数有具体描述，不要模糊 |
| **要求引用证据** | 评分必须引用具体内容，不能凭感觉 |
| **校准human** | 定期用人工评分校准model-based评分 |
| **避免位置偏见** | 评分时随机排列候选答案顺序 |
| **避免冗长偏见** | 不要因为输出长就打高分 |

## 四、Human Grader（人工抽检）

### 4.1 什么时候需要人工抽检

| 场景 | 抽检比例 |
|------|---------|
| 新技能上线前 | 100%人工评审 |
| 日常运行 | 10%抽检 |
| model-based评分异常 | 100%复核 |
| 用户投诉 | 100%复核 |

### 4.2 人工抽检清单

- [ ] 输出是否解决了用户的实际问题？
- [ ] 有没有事实错误/计算错误？
- [ ] 有没有遗漏重要信息？
- [ ] 格式是否易读？
- [ ] 建议是否合理可执行？
- [ ] 有没有过度承诺/误导？

## 五、Baseline对比（必须做）

### 5.1 什么是baseline

**Baseline = 不使用技能时，Claude原生完成任务的表现。**

### 5.2 为什么必须做baseline

```
❌ 常见错误：
  写了技能 → 跑eval → 80分 → "技能有效！"
  实际上：不写技能可能也有75分，技能只提升了5分

✅ 正确做法：
  1. 先跑baseline（不用技能）→ 记录分数
  2. 再跑技能版（用技能）→ 记录分数
  3. 对比提升幅度：>20%才算有价值
```

### 5.3 Baseline对比模板

```markdown
## 技能效果评估

| 指标 | Baseline（无技能） | 技能版 | 提升 |
|------|-------------------|--------|------|
| 任务完成率 | 60% | 90% | +30% |
| 输出完整率 | 40% | 95% | +55% |
| 平均评分（model-based） | 3.2/5 | 4.1/5 | +0.9 |
| 平均token消耗 | 2000 | 3500 | +75% |
| 平均时间 | 15s | 25s | +67% |

## 结论
技能在"输出完整率"和"任务完成率"上提升显著，
但token消耗增加75%。权衡后认为值得。
```

## 六、Eval-driven Development流程

### 6.1 RED-GREEN-REFACTOR

```
Step 1 (RED)：先写eval用例
  - 写3个测试场景（正常/边界/异常）
  - 定义通过标准
  - 运行eval → 失败（还没写技能）

Step 2 (GREEN)：写技能
  - 写最小可用技能
  - 运行eval → 通过

Step 3 (REFACTOR)：优化
  - 简化技能内容
  - 重新运行eval → 仍然通过
```

### 6.2 Eval用例设计模板

```json
{
  "skill_name": "my-skill",
  "evals": [
    {
      "name": "normal_case",
      "query": "用户正常请求",
      "expected_behavior": [
        "必须输出路由行",
        "必须调用validator脚本",
        "必须包含所有必需字段"
      ],
      "grader": "code-based",
      "pass_criteria": "所有code-based检查通过"
    },
    {
      "name": "edge_case",
      "query": "用户边界请求",
      "expected_behavior": [
        "必须优雅处理异常输入",
        "不能崩溃",
        "必须给出友好错误提示"
      ],
      "grader": "code-based + model-based",
      "pass_criteria": "code-based通过且model-based≥3.5/5"
    },
    {
      "name": "quality_check",
      "query": "用户深度请求",
      "expected_behavior": "输出质量评分≥4.0/5",
      "grader": "model-based",
      "pass_criteria": "model-based评分≥4.0"
    }
  ]
}
```

## 七、检查清单

- [ ] 是否同时使用了三种grader？
- [ ] code-based检查是否覆盖所有结构化要求？
- [ ] model-based评分标准是否具体到每个分数？
- [ ] 是否做了baseline对比？
- [ ] eval用例是否在写技能之前就写了？
- [ ] 是否定期用human校准model-based评分？
- [ ] 评分结果是否记录并追踪趋势？

**0-2项**：评估严重不足，无法判断技能是否有效
**3-5项**：评估基本完整，但缺少baseline或human校准
**6-7项**：评估完整，技能改进有数据支撑
