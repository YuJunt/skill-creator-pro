# 代码审查专家（Code Reviewer）

> **设计哲学**: Process型（方法论型）——基于固定的审查流程和Checklist，AI按步骤执行，不允许跳步。

> **预加载**: 触发后先确认审查范围（单文件/MR/PR/分支），再读取对应的references文档。

## 审查流程（6步，不可跳步）

### 第1步：确认审查范围（高自由度）
- 确认要审查的代码（文件路径/MR链接/分支名）
- 确认编程语言（Python/Java/Go/JavaScript等）
- 确认审查重点（安全/性能/可维护性/全部）

### 第2步：读取代码（低自由度）
- 必须完整读取所有待审查的代码文件
- 不允许只看部分代码就下结论
- 对于MR/PR，必须读取diff的完整内容

### 第3步：按Checklist逐项审查（低自由度）
必须按以下5个维度逐项审查，每个维度至少检查3项：

**维度1：安全性（最高优先级）**
- [ ] 是否有SQL注入风险（用户输入直接拼接SQL）
- [ ] 是否有XSS风险（用户输入直接输出到HTML）
- [ ] 是否有命令注入风险（用户输入传入shell命令）
- [ ] 是否有硬编码的密钥/密码/Token
- [ ] 是否有路径遍历风险（用户输入控制文件路径）
- [ ] 是否有不安全的反序列化（pickle/yaml.load等）

**维度2：性能**
- [ ] 是否有N+1查询（循环中执行数据库查询）
- [ ] 是否有不必要的大循环（O(n²)可以优化为O(n)）
- [ ] 是否有内存泄漏（大对象未释放/全局累积）
- [ ] 是否有重复计算（相同结果计算多次）

**维度3：可维护性**
- [ ] 函数是否过长（超过50行建议拆分）
- [ ] 是否有重复代码（DRY原则）
- [ ] 命名是否清晰（变量/函数/类名表达意图）
- [ ] 是否有魔法数字（硬编码的数字应定义为常量）
- [ ] 注释是否准确（过时的注释比没有注释更糟）

**维度4：可读性**
- [ ] 代码结构是否清晰（缩进/空行/分组）
- [ ] 嵌套是否过深（超过3层建议提前返回）
- [ ] 异常处理是否清晰（不吞异常/不裸except）

**维度5：测试覆盖**
- [ ] 新增代码是否有对应的单元测试
- [ ] 边界条件是否有测试（空值/最大值/异常输入）
- [ ] 测试是否有断言（不是只运行不验证）

### 第4步：问题分级（中自由度）
每个发现的问题必须分级：
- **严重（Critical）**：安全漏洞/数据丢失/系统崩溃，必须修复
- **高（High）**：性能瓶颈/逻辑错误/可维护性严重问题，建议修复
- **中（Medium）**：代码风格/命名/注释问题，择机修复
- **低（Low）**：建议优化/最佳实践，可选修复

### 第5步：输出审查报告（低自由度）
必须包含：
1. 审查范围（文件列表/行数/MR号）
2. 问题汇总（按严重程度统计）
3. 详细问题清单（每个问题：位置/描述/严重程度/修复建议）
4. 总体评价（通过/有条件通过/不通过）
5. 后续建议

### 第6步：验证修复（可选）
如果用户提供了修复后的代码，验证问题是否已修复。

## 完整示例（端到端）

**用户输入**："审查这个MR：https://github.com/example/repo/pull/123"

**第1步 确认范围**：MR #123，Python语言，审查重点：安全+性能

**第2步 读取代码**：
```python
def get_user(user_id):
    query = f"SELECT * FROM users WHERE id = {user_id}"
    return db.execute(query)

def get_all_users():
    users = []
    for id in range(1000):
        users.append(get_user(id))
    return users
```

**第3步 Checklist逐项审查**：
- 安全性：❌ `user_id`直接拼接SQL，有SQL注入风险
- 性能：❌ 循环中调用`get_user`，N+1查询
- 可维护性：✅ 函数名清晰
- 可读性：✅ 代码结构清晰
- 测试：❌ 没有单元测试

**第4步 问题分级**：
1. **严重** SQL注入（第2行）→ 改用参数化查询
2. **高** N+1查询（第6行）→ 改用批量查询
3. **中** 缺测试（整个文件）→ 补充pytest

**第5步 输出报告**：按输出格式模板填写

**第6步 验证循环**：
- 用户修复后 → 验证修复是否生效 → 未修复的问题继续跟踪
- 执行→验证→修正，形成闭环，不允许执行完就完事

## Gotchas（常见坑）

1. **只看diff不看上下文**：MR审查时只看改动行，不看改动的函数/类的完整上下文，容易漏判
2. **过度关注风格**：把时间花在空格/换行等风格问题上，忽略了真正的逻辑/安全问题
3. **不验证假设**："这个函数应该是安全的"——必须实际检查，不能假设
4. **报告太笼统**："这里有性能问题"不如"这个循环在1000条数据时会执行100万次查询，建议批量查询"
5. **忽略测试代码**：测试代码也需要审查，糟糕的测试比没有测试更危险
6. **不考虑业务逻辑**：代码审查不仅是技术问题，还要考虑业务逻辑是否正确
7. **一次审查太多**：超过400行的diff审查质量会下降，建议分多次审查

```markdown
# 代码审查报告

## 基本信息
- 审查范围: {文件列表/MR号}
- 编程语言: {语言}
- 审查时间: {时间}

## 问题汇总
| 严重程度 | 数量 |
|---------|------|
| 严重 | {n} |
| 高 | {n} |
| 中 | {n} |
| 低 | {n} |

## 详细问题清单
### 严重问题（必须修复）
1. **{问题标题}**
   - 位置: {文件}:{行号}
   - 描述: {具体描述}
   - 修复建议: {具体建议}

## 总体评价
- [ ] ✅ 通过（无严重/高优先级问题）
- [ ] ⚠️ 有条件通过（严重问题已修复，高优先级问题有修复计划）
- [ ] ❌ 不通过（有未修复的严重问题）
```
